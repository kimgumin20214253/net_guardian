# 경량 L4 지표 기반 Modbus TCP 제어망 장애 원인 판별의 한계 분석

전재우\*, 김구민\*, 김승현\*
\*국립순천대학교 인공지능공학부
e-mail: (교신저자 이메일)

**Analysis of the Limitations of Fault Cause Identification in Modbus TCP Control Networks Using Lightweight L4 Metrics**

Jae-Woo Jeon\*, (김구민 영문)\*, Seung-Hyun Kim\*
\*Dept. of Artificial Intelligence Engineering, Sunchon National University

## 요 약
본 논문은 패킷 내용을 해석하지 않고 측정할 수 있는 RTT, 손실 여부, 지터의 경량 L4 지표만으로 Modbus TCP 제어망의 장애 원인을 어디까지 판별할 수 있는지 분석하였다. tc netem 테스트베드에서 정상 상태와 지연, 유실, 복합의 세 가지 장애 상황을 재현하여 22,873건의 데이터를 수집하고 Random Forest 모델을 학습한 결과, 지연 장애는 재현율 0.98로 판별되었으며 30일 뒤 재수집한 데이터에서도 Macro F1 0.746으로 성능이 유지되었다. 유실 장애는 TCP 재전송으로 인해 타임아웃이 아닌 지연으로 관측되어 판별이 어려웠으나, TCP의 재전송 타이머(RTO) 계산 방식을 특징으로 도입하여 유실 재현율을 0.51에서 0.93으로 향상하였고, 실측한 재전송과의 대조에서 RTO 초과 판정의 정밀도는 94%였다. 학습하지 않은 장애 강도에서는 Macro F1이 0.533으로 낮아져 일반화에 한계가 있었다.

## 1. 서론
산업 제어 시스템은 공정을 실시간으로 제어하므로 통신 지연이나 패킷 유실이 설비 오작동과 안전사고로 이어질 수 있으며, 이에 따라 제어망에는 일반 정보망보다 엄격한 시간 성능이 요구된다[1]. Modbus TCP는 Modbus 메시지를 TCP/IP 위에서 요청-응답 방식으로 주고받는 산업용 프로토콜이다[2]. 제어망의 장애를 탐지하는 방법으로 패킷 내용을 분석하는 심층 패킷 분석(DPI)이 있으나, 이 방식은 프로토콜마다 패킷 구조를 해석해야 한다. 또한 장애 여부만 판단하는 이진 분류 방식은 장애가 발생했다는 사실만 알려 줄 뿐 원인을 구분하지 못한다. 지연과 유실은 대응 방법이 다르므로, 장애의 발생뿐 아니라 그 원인을 판별할 수 있어야 한다.

따라서 본 논문은 패킷 내용 없이 모든 TCP 통신에서 측정할 수 있는 RTT, 손실 여부, 지터에 주목하여, 이 지표만으로 장애 원인을 어디까지 판별할 수 있는지와 그 한계가 어디에서 비롯되는지를 분석하였다. 이를 위해 tc netem 기반의 장애 재현 테스트베드를 구축하고, 시간 블록 교차검증과 세 차례의 독립 세션으로 판별 성능의 재현성과 일반화 범위를 평가하였다. 또한 유실 장애가 지연으로 관측되는 원인을 TCP 재전송에서 찾고, TCP의 재전송 타이머 계산 방식을 판별 특징으로 도입한 뒤 실제 재전송과 요청 단위로 대조하여 검증하였다.

## 2. 장애 판별 시스템 구성
그림 1은 본 논문의 장애 판별 시스템 구성을 나타낸다. 테스트베드는 한 Linux 호스트에서 Modbus TCP 클라이언트와 서버를 실행하고, 둘 사이의 통신이 지나는 루프백(lo) 인터페이스에 tc netem[3]으로 장애를 주입하는 구조이다. 클라이언트가 수집한 데이터는 특징 생성과 장애 원인 판별을 거쳐 성능 검증에 사용되며, TCP 재전송 횟수는 nstat과 요청별 재전송 카운터로 별도 측정하여 판별 결과의 원인 분석과 검증에 활용하였다.

**[그림 1]** `figures/fig_system_bw.png`
그림 1. 장애 판별 시스템 구성도

클라이언트는 쓰기와 읽기 요청을 함께 보내고, 두 응답이 모두 도착할 때까지의 시간을 RTT로 기록한 뒤 0.1초 후 다음 요청을 보낸다. 1초 안에 응답이 없으면 유실(loss_flag=1)로 기록하고 RTT는 5000ms로 둔다. lo 인터페이스에서는 지연이 요청과 응답에 각각 적용되어 실측 RTT가 설정값의 2배 이상이 된다(설정 120ms → 실측 약 290ms). 따라서 netem 설정값 대신 매 요청의 실측 RTT를 판별에 사용하였다.

## 3. 실험 파라미터 설정
표 1은 장애 시나리오별 netem 설정과 수집 건수를 나타낸다. 시나리오는 A→B→A→C→A→D 순서로 순환하였으며, 복합 장애(D)는 정상 5초 후 지연 800ms·손실 40%(3초), 손실 100%(7초), 지연 300ms·손실 5%(5초)를 차례로 적용하였다. 수집 데이터는 총 22,873건이며 정상 상태가 71.5%를 차지한다.

**표 1. 장애 시나리오와 수집 건수 (A·B·C 각 30초, D 20초)**
| 구분 | netem 설정 | 건수 |
|---|---|---|
| A 정상 | 지연 1ms | 16,345 |
| B 지연 | 지연 120±40ms | 1,759 |
| C 유실 | GE 손실 모델 (p=5%, r=50%) | 3,521 |
| D 복합 | 4단계 (본문 참조) | 1,248 |

유실 장애에는 Gilbert-Elliott(GE) 손실 모델[4]을 사용하였다. 실제 네트워크의 패킷 손실은 독립적으로 발생하기보다 연속하여 몰리는 버스트 형태로 나타나므로, 정상 상태와 손실 상태를 오가는 2상태 모델로 이를 재현하였다. p는 정상 상태에서 손실 상태로, r은 손실 상태에서 정상 상태로 넘어갈 확률이며, 손실 상태에서는 패킷의 90%가 버려지고 정상 상태에서는 버려지지 않도록 설정하였다. 이 설정에서 평균 버스트 길이는 1/r = 2패킷, 이론상 평균 손실률은 약 8.2%이다.

기본 특징은 RTT, 손실 여부(loss_flag), 연속한 두 RTT 차의 절댓값인 지터의 세 가지이다. 처리량은 Modbus 패킷의 크기가 작고 일정하여 변별력이 낮으므로 제외하였다. 이에 더해 두 가지 특징 세트를 정의하였다. 윈도우 특징은 최근 15개 샘플의 손실률과 RTT 표준편차이다. TCP 방식 특징은 TCP의 재전송 타이머 계산 방식[5]을 따른다. 요청마다 RTT의 평활 평균(SRTT)과 변동폭(RTTVAR)을 갱신하고 재전송 기준 시간을 RTO = max(200ms, SRTT + 4·RTTVAR)로 계산하되, 타임아웃과 직전 RTO를 갑자기 초과한 응답은 재전송이 섞인 샘플로 보고 SRTT 계산에서 제외하였다(Karn 알고리즘)[5]. 최종적으로 SRTT, RTTVAR, 최근 15개 응답 중 RTO를 초과한 비율을 특징으로 사용하였다.

특징과 라벨이 완전히 같은 중복 879건을 제거한 21,994건을 8:2로 나누어 Logistic Regression(LR), Decision Tree(DT), Random Forest(RF), LightGBM을 비교한 결과, 클래스 불균형의 영향을 덜 받는 Macro F1에서 RF가 0.629(정확도 74.24%)로 가장 높아 판별 모델로 선정하였다. 이후 모든 비교는 같은 RF에서 특징 세트만 바꾸어 수행하였다.

## 4. 성능 분석 및 시험 결과
판별 성능은 네 가지 방법으로 평가하였다. 먼저 인접한 시점의 샘플이 학습과 평가에 함께 들어가 성능이 부풀려지는 것을 막기 위해, 각 시나리오 데이터를 시간 순서대로 5개 블록으로 나누어 교차검증하였다. 다음으로 원 데이터 전체로 학습한 모델을 다시 학습하지 않고 세 개의 독립 세션에 적용하였다. 재수집 세션(12,233건)은 30일 뒤 같은 설정으로, 일반화 세션(11,346건)은 B의 지연을 60ms와 200ms로, C의 p를 2%와 10%로 바꾸고 D의 강도를 변경하여 수집하였다. 검증 세션(10,988건)은 같은 설정에서 요청마다 운영체제의 TCP 재전송 카운터를 함께 기록하였다.

**표 2. 특징 세트별 Macro F1 (괄호: 유실 재현율, 모두 RF)**
| 검증 | 기본 | +윈도우 | +TCP 방식 |
|---|---|---|---|
| 시간 블록 5-fold | 0.683 (0.51) | 0.833 (0.90) | 0.748 (0.93) |
| 재수집 세션 | 0.746 (0.72) | 0.747 (0.87) | 0.711 (0.92) |
| 일반화 세션 | 0.533 (0.43) | 0.625 (0.76) | 0.549 (0.83) |
| 검증 세션 | 0.692 (0.55) | 0.730 (0.80) | 0.694 (0.81) |

표 2는 같은 RF에서 특징 세트만 바꾼 결과이다. 기본 특징만으로도 지연 장애의 재현율은 시간 블록 검증과 재수집 세션에서 0.98 이상이었고, 재수집 세션의 장애 구간 33개는 모두 탐지되었으며 구간 시작부터 탐지까지의 시간은 중앙값 1초 이내였다. 반면 유실 재현율은 0.43~0.72에 그쳤다. TCP 방식 특징은 네 가지 검증 모두에서 유실 재현율을 크게 높였으며(예: 시간 블록 0.51 → 0.93, 일반화 세션 0.43 → 0.83), 전체 Macro F1은 윈도우 특징이 가장 높았다.

유실 조건에서 Macro F1이 낮은 원인은 TCP 재전송에 있다. 정상과 유실 조건을 각각 60초간 측정한 결과, 유실 조건의 TCP 재전송 비율은 송신 세그먼트의 5.67%로 정상(0.12%)보다 크게 높았으나 Modbus 타임아웃은 2건뿐이었다. 그림 2와 같이 유실 조건의 지연 응답은 대부분 200ms 이상에 분포하였다. TCP는 손실된 세그먼트를 재전송 대기시간이 지난 뒤 다시 보내며[5], Linux는 이 대기시간의 최솟값으로 200ms를 사용한다. 즉 손실된 패킷은 재전송으로 복구되어 응용 계층에서는 타임아웃이 아닌 지연으로 관측되며, 이로 인해 기본 특징에서 손실 여부 특징의 중요도는 0.008에 그쳤다.

**표 3. 검증 세션의 장애 유형별 재전송과 RTO 초과 판정**
| 항목 | 정상(A) | 지연(B) | 유실(C) |
|---|---|---|---|
| 재전송이 발생한 요청 비율 | 4.3% | 25.1% | 19.6% |
| RTO 초과 판정 비율 | 0.2% | 3.6% | 8.1% |
| RTO 초과 중 실제 재전송 (정밀도) | 100% | 60% | 100% |
| 재전송 중 RTO 초과로 탐지 (탐지율) | 4.0% | 8.7% | 42.9% |

표 3은 검증 세션에서 RTO 초과 판정을 실제 재전송과 요청 단위로 대조한 결과이다. RTO를 초과한 응답 202건 중 190건(94%)에서 실제 재전송이 확인되었고, 유실 조건에서는 159건 모두 일치하였다. 다만 유실 조건의 재전송 중 RTO 초과로 탐지된 비율은 43%였는데, 이는 Linux TCP가 RTO 이전에 손실을 복구하는 경우 응답 지연이 RTO 기준에 미치지 않기 때문이다. 또한 지연 조건에서도 패킷 순서 변경으로 요청의 25%에서 재전송이 발생하였으므로, 재전송 정보는 단독이 아니라 RTT 수준과 함께 사용할 때 유실 판별에 유효하다.

복합 장애의 낮은 재현율은 시나리오 구성에서 비롯되었다. D 샘플의 69.6%는 정상 설정으로 둔 첫 5초 구간에서 수집되었으며, 이 구간의 RTT 중앙값(15.6ms)은 정상(15.9ms)과 같은 수준이었고 손실률(0.3%)도 정상(0.5%)과 비슷하였다. 이 구간을 제외하면 시간 블록 검증에서 기본 특징 RF의 Macro F1은 0.683에서 0.808로, 복합 재현율은 0.28에서 0.73으로 향상되었다.

일반화 세션에서는 학습하지 않은 지연 강도에서 성능이 낮아졌다. 학습 조건(120ms, 실측 약 290ms)의 지연 재현율은 0.98이었으나, 60ms(실측 약 155ms)에서는 0.14~0.21, 200ms(실측 약 443~495ms)에서는 0.57~0.83이었다. 지연이 학습 조건보다 약한 경우뿐 아니라 강한 경우에도 재현율이 떨어졌으므로, 모델은 학습 시 관측한 RTT 범위를 벗어난 지연을 일관되게 판별하지 못하였다.

## 5. 결론
본 논문은 패킷 내용을 해석하지 않는 경량 L4 지표만으로 Modbus TCP 제어망의 장애 원인을 판별할 수 있는 범위를 실측으로 분석하였다. 지연 장애는 재현율 0.98로 판별되었고 30일 뒤 재수집한 데이터에서도 성능이 유지되었으며, 장애 구간을 모두 1초 안팎에 탐지하였다. 유실 장애가 TCP 재전송으로 인해 지연으로 관측되는 문제는 TCP의 재전송 타이머 계산 방식을 특징으로 도입하여 개선하였으며(유실 재현율 0.51 → 0.93), 실제 재전송과의 요청 단위 대조로 그 타당성을 확인하였다(정밀도 94%). 다만 학습하지 않은 장애 강도에서는 판별 성능이 낮아졌고, RTO 이전에 복구되는 재전송은 탐지하지 못하는 한계가 있었다. 향후에는 여러 단계의 장애 강도로 학습 데이터를 확장하고, RTO 이전에 복구되는 재전송까지 포착하도록 판정 기준을 개선하며, 실제 산업망 트래픽에서 검증할 예정이다.
