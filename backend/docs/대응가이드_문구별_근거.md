# 11가지 대응가이드 — 문구별 근거 상세 (파일·페이지·부분)

이 문서는 `backend/fault_tiers.py`의 `action_guide` 조치 문구를 **한 줄씩** 뜯어서, 각 줄이
어느 PDF의 몇 페이지·어느 부분에서 나온 건지, 아니면 외부 근거 없이 **팀이 작성한 절차**인지를
명확히 구분한다. "검증됨"은 원문 PDF를 직접 읽고 대조한 것만 쓴다.

**사용한 3개 PDF** (`backend/docs/references/`):
- `NIST.SP.800-82r3.pdf`
- `E-96-2011 산업용 기계설비의 비상정지장치 설계에 관한 기술지침.pdf`
- `G-135-2021 스마트팩토리 안전시스템 평가에 관한 기술지침.pdf`

---

## 지연 (B)

### `b1` 순수 지연

| 조치 문구 | 근거 |
|---|---|
| 1. 스위치 포트별 출력 드롭 카운터 점검 | 팀 작성 절차 (일반적 네트워크 점검 관행, 1차 출처 없음) |
| 2. Modbus TCP 502 포트에 CoS/QoS 정책 적용 | 팀 작성 절차 (1차 출처 없음) |
| 3. 비업무 트래픽 대역폭 제한 | 팀 작성 절차 (1차 출처 없음) |
| *(이 사례를 왜 "기준 케이스"로 두는지)* | **검증됨** — `NIST.SP.800-82r3.pdf` **46페이지**(인쇄쪽수 29), 소제목 "Comparing OT and IT System Security"의 "Timeliness and performance requirements" 항목: 지연/지터 허용 기준이 설비마다 다르다는 원칙 |

### `b2` 재전송 신호 혼재

| 조치 문구 | 근거 |
|---|---|
| 1~2. 지연 조치 + reordering/재전송 모니터링 | 팀 작성 절차 |
| 3. 유실 가이드로 전환 검토 | 팀 작성 절차 |
| *(이 사례가 왜 나뉘는지)* | **검증됨, 단 PDF 아님** — 이 프로젝트 논문 표3 "지연 조건에서도 패킷 순서 변경으로 25% 재전송 발생" + `inspect_fault_tiers.py` 4번 출력(16.5%). PDF 3종과는 무관한 이 프로젝트 자체 데이터 근거 |

## 유실 (C)

### `c0` 0단계

| 조치 문구 | 근거 |
|---|---|
| 1. CRC/FCS 에러 카운트 확인 | 팀 작성 절차 |
| 2. 모니터링 유지 | 팀 작성 절차 |
| *(참고로 달아둔 표준)* | **미검증** — NIST SP 800-82 **Rev.2** §6.2.11.3 참고. 우리가 가진 PDF는 **Rev.3**뿐이라 Rev.2 원문은 못 열어봤음(기존 `manual_knowledge_base.json`에서부터 "팀 재정리, 축자 인용 아님"으로 표시되어 있던 부분을 그대로 가져온 것) |

### `c1`~`c4` (1~4단계, 공통 구조)

| 조치 문구 | 근거 |
|---|---|
| CRC/FCS 확인, 차폐케이블·접지 점검, 광케이블 교체 검토 | 팀 작성 절차 (NIST Rev.2 §6.2.11.3 참고 — 위와 동일하게 미검증) |
| **"통신 끊김 시 멈추는지/계속 도는지, 상태경보 뜨는지 확인"** | **검증됨** — 아래 2개 원문 그대로 |
| | ① `NIST.SP.800-82r3.pdf` **96페이지**(인쇄쪽수 79), §5.3.1 "Cyber-Related Safety Considerations": 통신 손실이 fail-safe 이벤트를 유발할 수 있다는 원문 |
| | ② `G-135-2021...pdf` **23페이지**(문서쪽수 "-20-"), "공정설비 안전설계 및 구성 > 안전제어시스템" 분야 문항90: "안전PLC와 제어기기의 통신이 올바르지 않을 경우 상태경보등 또는 경보음을 발생시키는가?" |
| | ③ `G-135-2021...pdf` **16페이지**(문서쪽수 "-13-"), "정보(통신)운영기술 및 통신네트워크" 분야 문항26: 안전전용 네트워크 분리 여부 |
| 단계별 비중(21.0/31.5/30.3/12.4/5.1%) | 이 프로젝트 자체 데이터 — `inspect_fault_tiers.py` 5번 출력 |

**정리**: 유실 가이드에서 "통신 이상 시 경보/fail-safe 확인하라"는 핵심 문구는 3개 PDF 전부에서 원문으로 뒷받침되지만, "차폐케이블·접지·광케이블" 같은 물리계층 구체 조치는 아직 미검증 상태입니다.

## 복합 (D)

### `d1` 전환 초기

| 조치 문구 | 근거 |
|---|---|
| "아직 지켜보는 단계, 잠시 후 재평가" | **PDF 근거 없음** — 외부 표준이 아니라 이 프로젝트 실험 설계의 과도구간(69.6%). `analyze_followup.py` 세그먼트 분석 결과 |

### `d2_low`/`d2_mid`/`d2_high` (공통 구조)

| 조치 문구 | 근거 |
|---|---|
| **"사람(작업자) 안전 확인을 최우선으로"** | **검증됨** — `E-96-2011...pdf` **7페이지**(문서쪽수 "-5-"), §4.1(7) "비상정지신호는 다른 신호보다 우선" / §4.1(8) "응답이 추가 위험을 유발해선 안 됨" |
| **"이중화 경로/링 토폴로지 자동 절체 확인"** | **검증됨** — `NIST.SP.800-82r3.pdf` **46페이지**(인쇄쪽수 29) "Availability requirements" 항목("Some OT employ redundant components...") + **21페이지**(인쇄쪽수 4) Executive Summary의 defense-in-depth 목록("Ensuring that critical components are redundant...") |
| "스위치 로그에서 flapping 이력 점검" | **미검증** — NIST Rev.2 §5.6/§5.13 참고(Rev.2 원문 없음, 기존 `manual_knowledge_base.json`에서부터 미검증 상태였던 부분) |
| (`d2_high`만) "수동 운전 모드 전환 준비" | **미검증, 팀 작성 절차** — KOSHA 산업용 로봇 관련 지침(M-61-2017)에 운전모드 전환 스위치 관련 내용이 있다는 건 검색 스니펫으로만 확인했고, 그 PDF는 링크가 죽어서 끝내 못 받음. 지금은 원문 근거가 없는 상태 |
| 단계별 비중(45.5/24.2/30.3%) | 이 프로젝트 자체 데이터 — `inspect_fault_tiers.py` 6번 출력 |

**정리**: 복합 가이드에서 "사람 안전 우선"과 "이중화 확인"은 2개 PDF로 확실히 뒷받침되지만, "flapping 로그 점검"과 "수동 운전 전환"은 아직 미검증 — 특히 수동 운전 전환은 KOSHA M-61-2017 원문을 못 받아서 생긴 공백입니다.

## 전체 요약 — 무엇이 검증됐고 무엇이 아직 아닌지

| 상태 | 해당 문구 |
|---|---|
| ✅ 3개 PDF 원문으로 검증 | 유실의 "통신 이상 시 경보/fail-safe 확인", 복합의 "사람 안전 우선"·"이중화 확인" |
| ⚠️ 이 프로젝트 데이터로 검증(PDF 아님) | 지연의 "재전송 신호 혼재" 구분, 복합의 "첫 5초 과도구간", 모든 사례의 단계별 비중(%) |
| ❌ 미검증 (팀 작성 절차 또는 원문 못 구함) | CRC/FCS, 차폐케이블/접지, 광케이블 교체, flapping 로그 점검, 수동 운전 전환 |

미검증 항목은 **틀렸다는 뜻이 아니라, 아직 공식 문서 원문으로 대조를 안 해봤다는 뜻**입니다. 발표/보고 시에는 이 구분을 그대로 밝히는 게 안전합니다.
