# 장애 대응가이드를 위한 안전기준/설계원칙 조사 (2026-11-14)

## 0. 조사 배경과 신뢰도 안내

지금 `backend/docs/manual_knowledge_base.json`에는 지연(B)·유실(C)·복합(D) 각 1개씩, 총 4개 문서만 있고, 각 문서의 `action_guide`는 팀이 NIST SP 800-82 Rev.2의 취지를 재정리한 짧은 3줄짜리 절차다. AI 추천 가이드 기능을 붙이기 전에, 유형별로 비어 있던 영역(제어루프 타임아웃 기준, fail-safe 동작, 단계적 정지, 재가동 절차 등)을 보강할 자료를 찾아봤다.

**신뢰도 구분이 중요하다.** 검색으로 나온 자료는 세 등급으로 나뉜다:

- **A급 (표준/규격 문서, 원문 미확인)**: KOSHA 기술지침(E-96-2011, G-135-2021), KS B ISO 13850/13849-1, KS C IEC 61800-5-2, IEC 61508/61511, RFC 6298/8985 — 공신력은 있지만 **이번 조사는 원문 PDF를 직접 읽은 게 아니라 2차 자료(검색 스니펫)로 확인한 것**이므로, 실제로 지식베이스에 넣기 전에 원문 대조가 반드시 필요하다.
- **B급 (업체/실무 블로그, 포럼)**: industrialmonitordirect.com, Promwad, 알체라(Alchera) 블로그 등 — 실무적으로는 유용하지만 표준이 아니라 업체 자체 경험/권고다. 수치(ms, 초)는 대부분 여기서 나왔는데, **공식 기준이 아니라 "관찰된 사례"**로만 취급해야 한다.
- **공백 (못 찾음)**: "산업현장 특화 RTO 튜닝", "네트워크 장애 전용 작업자 대응절차" 같은, 지금 이 프로젝트 상황에 정확히 맞는 문서는 끝내 못 찾았다. 이 프로젝트가 다루는 "Modbus TCP 재전송 타이머 기반 장애 판별"은 상당히 특수한 조합이라, 범용 표준에 직접적으로 대응되는 조항은 원래 없을 가능성이 높다 — 그래서 팀이 재정리하는 현재 방식(표준의 '취지'를 인용하고 구체 절차는 팀이 정의)이 애초에 맞는 접근이었다.

## 1. 지연 (Delay) 관련

### 1-1. Modbus TCP 타임아웃/폴링 주기 — 공식 수치 기준 없음 (B급)
- 타임아웃을 늘리는 것은 "증상 완화"일 뿐, 네트워크 지연이나 PLC 처리 속도 자체를 줄이지 않는다는 지적이 공통적으로 나온다.
- 제조사별로 하드웨어 고정값이 다르다: Siemens S7-1200 MB_CLIENT는 타임아웃 파라미터가 따로 없고 약 8초 고정, PLCnext 포럼 사례는 2000ms로 맞춰야 안정적이었다고 보고.
- 한 자료는 "장치의 idle 타임아웃 관찰값의 0.5배를 폴링 주기로 잡으라"는 실무 규칙을 제시.
- 공식 수치가 필요하면 IEC 61784/61158(필드버스 표준) 원문을 확인해야 한다는 포인터만 나왔다 — **원문 미확인**.

### 1-2. 지연 허용 기준(SLA)은 "네트워크가 아니라 공정에서 역산" (B급, Promwad)
- 지연 예산(latency budget)은 네트워크 측정값에서 시작하면 안 되고, **제어 대상 공정의 시간상수 + 안정 마진**에서 시작해 네트워크에 얼마를 배정할지 역산해야 한다는 원칙.
- p99/최대 지연과 지터를 스캔타임·제어주기 대비로 설정해야 하며, 평균 지연보다 "최악의 경우(worst-case) 지연"이 제어 루프 안정성에 더 중요하다는 지적.
- Deterministic Ethernet(TSN) 등이 최악 지연을 보장하는 대안으로 언급됨 (참고용).

**가이드 반영 아이디어**: 지금 "QoS 정책 적용"이라는 단일 조치 앞에, "이 지연이 공정 안정성에 실제로 영향을 주는 수준인지부터 판단"하는 단계를 추가할 수 있다 — 이게 지난번 분석한 RTT 180~540ms 구간별 심각도 구분과 맞아떨어진다.

## 2. 버스트 유실 (Burst Loss) 관련

### 2-1. 통신 끊김 시 Fail-safe vs Hold-last-state — 제조사마다 기본값이 다름 (B급)
- **Rockwell ControlLogix 계열**: 통신 끊기면 출력이 기본적으로 0(OFF)으로 감 (안전측 기본값).
- **Allen-Bradley PLC-5**: 기본값이 반대로 "마지막 상태 유지".
- 이 설정은 **컨트롤러-I/O 모듈 간 통신 두절에만 적용**되고, 프로세서 자체 고장 시에는 별도로 설정된 고장 상태로 전환된다.
- **안전 관련 기능은 IEC 61508/61511 기준**, 감지되지 않은 고장이 나면 반드시 안전측으로 fail해야 하며, 이런 경우 범용 PLC가 아니라 안전 PLC(예: Siemens F-CPU)를 별도로 쓰는 게 일반적이라는 설명.
- **워치독 패턴**: 상위 PLC가 주기적 하트비트를 보내고 타임아웃되면 출력을 안전상태로 강제. 외부 워치독 릴레이로 하드와이어 차단하는 방식도 있음 (PLC가 1Hz 펄스 전송 → 끊기면 외부 타이머가 전원 접촉기 차단).
- 적용 구분: 칠러·냉각수 펌프 같은 연속공정은 last-state 유지가 유리할 수 있지만, 안전이 걸린 공정은 생산 연속성보다 안전정지가 우선.

**가이드 반영 아이디어**: 지금 유실 가이드에 "이 설비가 통신 끊김 시 OFF인지 last-state 유지인지 먼저 확인"하는 체크 항목을 추가할 수 있다 — 설비 기본값을 모르고 대응하면 엉뚱한 방향으로 조치할 위험이 있다는 걸 이번 조사에서 확인함.

### 2-2. RTO/재전송 기반 버스트 판별 — 논문 주제와 직결 (A급, RFC)
- **RFC 6298**: RTO = SRTT(평활화 RTT) + 4×RTTVAR(RTT 변동), **최소 1초로 하한**이 걸려 있다. 이 "1초 floor"가 밀리초 단위 데드라인을 요구하는 산업제어 루프와 안 맞는다는 점이 지적되는데, 이게 정확히 이 논문의 "RTO 기반 버스트 손실/지연 판별 기능"이 다루는 문제와 일치한다.
- **RFC 8985 (RACK-TLP)**: 기존 DupAck 카운트 기반 손실 탐지보다, 타임스탬프+SACK 기반 탐지가 패킷 재정렬이나 application-limited 상황에서 더 효율적이라고 설명.
- RTO로 복구한 뒤 slow start 구간에서 다시 burst loss가 발생할 수 있다는 지적도 있음 — "장애 조치 후에도 한동안 재발 가능성이 있다"는 걸 가이드 문구에 반영할 수 있는 근거.
- 실측 도구: Wireshark의 `tcp.analysis.retransmission` 필터로 재전송 구간을 직접 확인 가능.
- **공백**: "산업현장 특화 RTO 튜닝" 자료는 이번 검색에 없었다. 후속 검색이 필요하면 `industrial TCP RTO tuning`, `Modbus TCP retransmission 최적화` 같은 키워드로 더 파볼 수 있다.

## 3. 복합 (Combined) 관련

### 3-1. 단계적 정지(감속 → 완전정지) (B급 블로그 + A급 표준 포인터)
- **알체라(Alchera) 블로그** (기업 블로그, 비공식): 완전 정지만 쓰면 사소한 신호에도 가동이 자주 멈춰 생산에 지장이 생기므로, 신호 심각도에 따라 **먼저 감속 → 위험이 안 풀리면 완전 정지**하는 단계적 구조를 제안. 여러 신호가 동시에 들어올 때를 대비해 우선순위를 미리 정하고, **사람 안전 관련 신호는 항상 최우선**으로 처리하라고 권고. 재가동 전에는 정지 원인을 하나씩 개별 확인·기록하고, 원격 해제 시에는 현장 카메라 확인을 먼저 거치도록 제안.
- **KOSHA G-135-2021 (스마트팩토리 안전지침)**이 인용하는 관련 표준: KS B ISO 13850(기계 안전 비상정지 설계원리), KS B ISO 13849-1(제어시스템 안전관련 부품 설계), KS C IEC 61800-5-2(가변속 구동 시스템 안전기능) — 감속정지처럼 속도 제어가 들어가면 특히 KS C IEC 61800-5-2가 관련될 가능성이 크다. **원문 미확인, 포털에서 직접 다운로드 필요**.

### 3-2. 비상정지 우선순위 원칙 (A급, KOSHA E-96-2011 — 원문 미확인)
- 비상정지 신호가 다른 모든 작동 신호보다 우선해야 한다.
- 비상정지에 대한 응답이 **또 다른 위험을 만들어서는 안 된다** (예: 급정지로 인한 2차 사고).
- 수동으로 작동시킨 비상정지는 제어장치가 **리셋되기 전까지 그 상태를 유지**해야 한다.
- 정지방식(기계 안전 표준에서 말하는 0정지/1정지 구분)의 세부 내용은 검색 스니펫만으로는 확인 안 됨 — **원문 확인 필요**.

### 3-3. 수동 운전 전환 및 재가동 (B급 사례 + A급 포인터)
- KOSHA 산업용 로봇 안전 기술지침: 자동/수동 운전을 바꾸는 전환 스위치와, 현재 운전 상태를 표시하는 램프를 갖추도록 요구.
- 해외 사고 사례: 작업자가 센서 고장을 조치하던 중 로봇이 예기치 않게 재작동해 사망 — 조치 중에는 정지 상태를 확실히 유지하는 **잠금·표시(LOTO) 절차**가 필요하다는 근거.
- 안전 조치 적용 후에는 엔지니어가 센서·인터록·비상정지 장치가 정상 작동하는지 검증해야 하고, 많은 안전회로는 **이중 채널 + 교차 감시** 구조를 쓴다는 설명.
- Yokogawa: 수동 운전 시 운전원마다 조치가 달라지는 편차를 줄이기 위해 표준작업절차서(SOP) 기반 접근을 권고.

## 4. 공통 — 못 찾은 것 / 원문 대조가 필요한 것

1. **정확한 수치 기준(몇 ms, 몇 초)은 공식 표준에서 거의 안 나온다.** 이건 당연한 결과다 — 표준은 보통 설계 원칙만 규정하고, 실제 수치는 설비별 위험성평가로 정하게 되어 있다. 따라서 "표준에서 숫자를 그대로 가져오겠다"는 접근보다, **이 프로젝트가 이미 갖고 있는 실측 데이터 기반 임계값(RTT 180~540ms 등)을 표준의 '설계 원칙'과 결합**하는 방향이 맞다.
2. KOSHA E-96-2011, G-135-2021 원문 조항 — portal.kosha.or.kr에서 직접 다운로드해 대조 필요.
3. KS B ISO 13850, KS B ISO 13849-1, KS C IEC 61800-5-2 원문 — 미확인.
4. "산업현장 특화 RTO 튜닝" — 이번 조사에서 공백으로 남음.

## 5. 지식베이스(`manual_knowledge_base.json`) 반영 제안

기존 4개 문서를 유지하면서, 각 문서의 `action_guide`에 아래와 같이 **단계를 추가**하는 방향을 제안한다 (표준 재정리 + 실측값 결합):

- **지연(B)**: "① 이 지연이 공정 안정성에 영향을 주는 수준인지 확인 (RTT 임계값 기준) → ② QoS 정책 적용 → ③ 조치 후에도 180ms 이상 지속되면 에스컬레이션"
- **유실(C)**: "① 이 설비의 통신 끊김 기본 동작(OFF/last-state) 확인 → ② CRC/FCS 에러 점검(기존) → ③ RTO 복구 직후에는 재발 가능성 있으므로 짧은 시간 재모니터링"
- **복합(D)**: "① 사람 안전 관련 신호 최우선 확인 → ② 감속 단계 적용 여부 확인 → ③ 이중화 절체(기존) → ④ 재가동 전 원인별 개별 확인·기록 → ⑤ 원격 해제 전 현장 확인"

각 문서의 `reference` 필드에는 이번에 확인한 출처를 "참고 출처"로 추가하되, 원문 미확인 항목(KOSHA 조항 등)은 **"원문 대조 필요"라고 명시**해서, 지금까지 이 프로젝트가 지켜온 인용 원칙(축자 인용 아님, 팀이 재정리)을 그대로 유지해야 한다.
