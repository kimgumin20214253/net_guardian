## 2. 교수님 피드백의 핵심

> "타임아웃이 아닌 지연처럼 관측되어 구별하기 어렵다" → **구별할 수 있는 방법이 있다.**

교수님이 추가로 강조하신 내용:
- TCP는 매번 RTT를 계산해 **재전송 기준 시간(RTO)**을 정한다. 이 시간 안에 응답이 없으면 재전송한다.
- 기준 시간은 하나의 값이 아니라 **여러 값(평균과 변동폭)**으로 계산한다.
- **손실·재전송이 섞인 RTT는 계산에서 뺀다.**
- 손실의 원인은 혼잡(라우터가 버림) 또는 전송 오류(깨짐)이며, **둘 다 "유실"(패킷이 사라짐)이다.** 혼잡과 손상을 구별하라는 뜻은 아니다.
- 지터는 지연의 편차라서, 지연이 일정하면 지터로는 잡을 수 없다.

즉 **"TCP의 재전송 기준 시간 방식으로 유실을 실제로 구별하고, 그 결과를 보여라"**는 뜻이다.

## 3. 해결 방법: TCP 방식 특징

### 아이디어 (택배 비유)
- TCP는 "보통 이 정도면 답이 온다"는 **기준 시간(RTO)**을 계속 계산한다.
- **지연 장애:** 모든 답이 골고루 느리게 온다. 평균 자체가 올라간다.
- **유실 장애:** 평소에는 빠른데, **가끔 기준 시간을 넘겨서** 온다. 사라진 패킷을 다시 보내느라 늦어진 것이다.
- 따라서 **"최근에 기준 시간을 넘겨 온 답이 몇 번 있었나"**를 세면 유실을 찾을 수 있다.

### 용어 정리: 손실, 재전송, 유실 장애
| 용어 | 뜻 | 택배 비유 |
|---|---|---|
| **손실** | 네트워크 중간에서 패킷이 사라진 **사건** | 택배가 배송 중에 없어짐 |
| **재전송** | 손실이 생기자 TCP가 **다시 보내는 행동** | 판매자가 같은 물건을 다시 보냄 |
| **유실 장애** | 손실이 자주 일어나는 **장애 상황** (시나리오 C) | 택배가 자주 없어지는 배송 구간 |

**손실이 원인이고, 재전송은 그 결과**이다. 둘 다 "유실 장애가 일어나고 있다"는 증거다.

우리 데이터에서 손실은 두 가지 모습으로 보인다.

| 모습 | 무슨 일이 있었나 | 우리 데이터에서 |
|---|---|---|
| **타임아웃** | 재전송까지 실패해서 1초 안에 답이 안 옴 | loss_flag = 1 |
| **늦은 응답** | 재전송으로 복구는 됐지만 기다리느라 늦게 옴 | RTT가 기준 시간(RTO)을 넘음 |

**두 모습 모두 유실의 증거로 본다.** 지금까지는 타임아웃만 유실로 세고 늦은 응답은 지연처럼 보고 있었기 때문에, 유실을 절반밖에 못 맞혔다(재현율 0.51).

### "RTT 계산에서 뺀다"의 뜻
**버리는 것이 아니라, 평균 계산에만 넣지 않고 따로 센다.**
- **평균 RTT(SRTT)에서 빼는 이유:** 손실·재전송이 섞인 RTT는 길이 얼마나 막히는지(지연)가 아니라 없어진 택배를 다시 보내느라 기다린 시간이다. 평균에 넣으면 평소 배송 시간이 왜곡된다.
- **대신 따로 세는 것:** 타임아웃 횟수(손실률), 기준 시간을 넘긴 횟수(RTO 초과 비율). 이것이 유실을 찾아내는 특징이 된다.

> 정리: **지연은 평균으로 보고, 유실은 평균에서 뺀 것들을 세어서 본다.**

### 정식 분석에서 보완할 점
- 탐색 분석에서는 **타임아웃만** 평균에서 뺐고, **늦은 응답은 평균에 그대로 넣었다.** 교수님 설명대로라면 늦은 응답도 빼야 한다.
- 다만 그대로 빼면 문제가 생긴다. 지연 장애가 **막 시작될 때**도 응답이 기준 시간을 넘기는데, 이것까지 모두 빼면 평균이 지연에 적응하지 못한다.
- 그래서 정식 분석에서는 다음처럼 구분한다. 교수님이 말씀하신 "유실은 가끔 튀고, 지연은 골고루 느리다"는 차이를 그대로 쓰는 방식이다.
  - **가끔 튀는 늦은 응답** → 재전송으로 보고 평균에서 제외 (유실)
  - **연속으로 늦은 응답** → 실제로 길이 느려진 것으로 보고 평균에 반영 (지연)
- 이 방식이 탐색 결과보다 나은지 비교한 뒤 논문에 쓸 방식을 정한다.

### 만드는 특징 (RFC 6298 계산 방식 그대로)
| 특징 | 의미 |
|---|---|
| SRTT | RTT 평균 (유실 샘플은 계산에서 제외) |
| RTTVAR | RTT 변동폭 (유실 샘플은 계산에서 제외) |
| RTO 초과 비율 | 최근 15개 응답 중 기준 시간(RTO)을 넘겨 온 비율 = **재전송 추정치** |

### 기존 데이터로 확인한 결과 (탐색 결과, 정식 분석 전 — 확정 숫자는 5번 참고)
**① RTO 초과 비율이 실제 재전송 비율과 거의 같다**

| | 정상(A) | 유실(C) |
|---|---|---|
| RTO 초과 비율 (원 데이터에서 계산) | 0.23% | 5.88% |
| 실제 TCP 재전송 비율 (nstat) | 0.12% | 5.67% |

→ 이 방법이 실제 재전송을 잘 잡아낸다는 근거.

**② 유실을 맞히는 비율이 크게 오른다** (시간 블록 검증, 모두 같은 RF 모델)

| 특징 | Macro F1 | 지연 | 유실 | 복합 |
|---|---|---|---|---|
| 기본 (RTT, 손실, 지터) | 0.683 | 0.99 | **0.51** | 0.28 |
| 기본 + 윈도우 | 0.831 | 0.99 | 0.90 | 0.46 |
| **TCP 방식** | 0.816 | 1.00 | **0.94** | 0.45 |
| 기본 + 윈도우 + TCP 방식 | 0.841 | 1.00 | 0.92 | 0.46 |

→ 유실 재현율 **0.51 → 0.94**. 교수님 질문에 대한 직접적인 답.

**남는 한계:** 처음 보는 지연 강도에서는 지연 재현율이 여전히 낮다(0.27~0.45). 지연이 일정하면 RTT 수준으로만 판단해야 한다는 교수님 지적과 같은 문제이며, 논문에는 한계로 쓴다.

### 이전 계획과 달라진 점
| | 이전 계획 | 새 계획 |
|---|---|---|
| 재전송을 알아내는 법 | 운영체제 재전송 카운터를 새로 기록 | RTT로 TCP 기준 시간 초과를 계산 |
| 필요한 데이터 | 수집기 수정 + 김구민 A~D 재수집 | **기존 데이터 그대로** |
| 결과 | 수집 후에야 알 수 있음 | **이미 나옴** |

### 함께 고칠 것: 모델 비교 방식
지금 원고는 **RF(기본 특징)와 DT(윈도우 특징)**를 비교한다. 모델과 특징이 동시에 달라 공정하지 않다.
→ **모두 RF로 맞춰서** 특징만 바꿔 비교한다(위 ② 표 방식).

## 5. 정식 분석 결과 (2026-10-09, 커밋 06aa1ef)

`eval_tcp_features.py`로 기존 실측 데이터를 다시 계산한 결과다. 결과 파일은 `results_tcp_features/`.
누구나 `cd backend` → `python eval_tcp_features.py`로 같은 숫자를 재현할 수 있다.

- 모든 비교는 **같은 Random Forest**로 했다. 특징 세트만 바꿨다.
- 평균 RTT(SRTT) 계산에서 타임아웃과 **갑자기 튄 늦은 응답**(재전송 추정)을 뺐다. 연속으로 늦으면 지연으로 보고 반영했다(교수님 설명 방식, 결과 파일의 `karn`).

**유실 재현율: 세 검증 모두에서 크게 올랐다**

| 특징 | 시간 블록 | 재수집 세션 | 일반화 세션 |
|---|---|---|---|
| 기본 (RTT, 손실, 지터) | 0.51 | 0.72 | 0.43 |
| 기본 + TCP 방식 | **0.93** | **0.92** | **0.83** |

**추정한 재전송이 실제와 맞는지** (nstat을 잰 같은 60초 데이터)

| | 정상(A) | 유실(C) |
|---|---|---|
| RTO를 넘긴 응답 (우리 방법) | 0건 / 574건 | 34건 / 415건 |
| 실제 TCP 재전송 (nstat) | 0.12% | 5.67% |

**정직하게 쓸 점:** TCP 방식은 유실을 잘 잡지만 전체 점수(Macro F1)를 가장 많이 올리는 것은 아니다.

| 특징 | 시간 블록 Macro F1 (5개 fold 평균) |
|---|---|
| 기본 | 0.683 |
| 기본 + 윈도우 | **0.833** (가장 높음) |
| 기본 + TCP 방식 | 0.748 |
| 전부 | 0.832 |

TCP 방식을 넣으면 지연 재현율이 조금 내려간다(재수집 세션 0.98 → 0.88). 논문에는 이렇게 쓴다.
- 유실 판별: TCP 방식으로 크게 개선 (교수님 질문에 대한 답)
- 전체 성능: 윈도우 특징이 가장 효과적
- "TCP 방식으로 모든 성능이 좋아졌다"고는 쓰지 않는다.

## 6. 실측 검증 수집 (김구민, 2026-10-09 완료)

### 왜 하나
위 결과는 "RTO를 넘긴 응답 = 재전송된 응답"이라는 **추정**에 기대고 있다. 지금은 60초 **전체 비율**로만 확인했다.
이번 수집에서는 요청마다 **운영체제가 센 실제 재전송 횟수(정답)**를 함께 기록해서, 요청 하나하나를 대조한다.
→ 논문에 "RTO 초과로 추정한 재전송은 실제 재전송과 ○○% 일치하였다"라고 쓸 수 있다.

### 바뀐 코드
- `packet_analyzer.py`(수집기)에만 기능을 추가했다. 서버와 `master_collector.sh`는 그대로다.
- Linux는 컴퓨터 전체의 TCP 재전송 횟수를 `/proc/net/snmp`에 계속 센다. 수집기가 **요청 직전과 응답 직후**에 이 숫자를 읽어 차이를 기록한다.
- 옵션(`PA_LOG_RETRANS=1`)을 켰을 때만 동작한다. 끄면 예전과 똑같은 파일이 만들어지므로 대시보드에 영향이 없다.

### 무엇을 수집하나 (요청 하나당 한 줄, 0.1초마다)
| 열 | 뜻 | 기존에도 있었나 |
|---|---|---|
| `timestamp` | 측정 시각 | ✅ |

## 7. 실측 검증 결과 (2026-10-09)

- **데이터:** `raw_dataset_20261009/verify_retrans.csv` (18:43~19:13, 약 30분, 10,988건, 재전송 열 모두 기록됨)
- **분석:** `python eval_verify_retrans.py` → 결과는 `results_tcp_features/verify_*.csv` 3개
- 요약: **좋은 소식 하나, 논문에 정직하게 써야 할 발견 두 가지**

### ① 좋은 소식: RTO 초과로 잡은 것은 거의 다 진짜 재전송이다
요청 하나하나를 운영체제가 센 실제 재전송과 대조했다(응답을 받은 요청 10,775건).

| | RTO 초과로 잡은 요청 | 그중 실제 재전송 | 정밀도 |
|---|---|---|---|
| 전체 | 202건 | 190건 | **94%** |
| 유실(C) | 159건 | 159건 | **100%** |
| 정상(A) | 13건 | 13건 | 100% |

"RTO를 넘겨 온 응답 = 재전송된 응답"이라는 추정은 맞다. 유실 조건에서는 잘못 잡은 것이 한 건도 없었다. **교수님 방식의 근거가 실측으로 확인됐다.**

**모델 성능도 재현됐다.** 원 데이터로 학습한 모델을 이번 새 데이터에 그대로 적용했다(네 번째 독립 세션).

| 특징 | 유실 재현율 | Macro F1 |
|---|---|---|
| 기본 | 0.55 | 0.692 |
| 기본 + TCP 방식 | **0.81** | 0.694 |
| 기본 + 윈도우 | 0.80 | 0.730 |

이번에도 "TCP 방식은 유실을 크게 개선하고, 전체 점수는 윈도우 특징이 가장 높다"는 같은 패턴이다.

### ② 발견: RTO 방식은 재전송의 일부만 잡는다
유실(C) 조건에서 실제 재전송이 있었던 요청 중 RTO 방식으로 잡은 것은 **43%**다(371건 중 159건).

- **놓친 이유:** Linux TCP는 손실이 생겨도 RTO까지 기다리지 않고 더 빨리 다시 보내는 경우가 많다(빠른 재전송 등). 이때 응답은 조금만 늦어진다.
- 놓친 요청의 RTT 중앙값은 약 34ms로, 평소(약 5~10ms)보다는 늦지만 RTO 기준(최소 200ms)에는 못 미친다. 놓친 요청의 89%는 평소 RTT의 1.5배 이상이었다.

→ 논문에 쓸 표현: "RTO 초과는 정확하지만(정밀도 94%) 보수적인 지표이며, RTO 이전에 복구되는 재전송은 탐지하지 못한다. 기준을 낮추면 더 많이 잡을 수 있으나 정상 구간의 오경보와의 균형이 필요하다(향후 과제)."

### ③ 발견: 지연 장애에서도 재전송이 일어난다
| 유형 | 재전송이 있었던 요청 비율 |
|---|---|
| 정상(A) | 4.3% |
| 지연(B) | **25.1%** |
| 유실(C) | 19.6% |

- netem의 지연 변동(120±40ms) 때문에 **패킷 순서가 뒤바뀌면서** TCP가 불필요하게 재전송하는 것으로 보인다.
- 다만 지연 조건에서 RTO 방식이 잡은 것은 3.6%로 적었고, 지연은 RTT 자체가 높아서(290ms) 유실과 헷갈리지 않는다.

→ **"재전송 = 유실"이라고 단정하면 안 된다.** 논문에는 "재전송 정보는 RTT 수준과 함께 쓸 때 유실 판별에 유효하다"로 쓴다. 심사위원이 먼저 지적하기 전에 우리가 밝히면 오히려 신뢰도가 올라간다.

### 논문에 들어가는 위치
| 위치 | 들어갈 내용 |
|---|---|
| 3장 실험 파라미터 설정 | TCP 방식 특징 정의 (SRTT, RTTVAR, RTO = max(200ms, SRTT + 4·RTTVAR), 재전송 섞인 샘플 제외, 최근 15개 중 RTO 초과 비율) |
| 4장 표 2 | 특징 세트 비교(기본 / +윈도우 / +TCP 방식, 모두 RF) × 검증 4가지(시간 블록, 재수집, 일반화, **검증 세션**) |
