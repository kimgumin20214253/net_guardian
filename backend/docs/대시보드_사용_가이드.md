# NET GUARDIAN 대시보드 사용 가이드

이 문서는 NET GUARDIAN(산업 네트워크 장애 관제 대시보드) 화면 구성과 각 기능, 그리고
AI 대응가이드가 어떤 근거와 알고리즘으로 동작하는지 한 군데에 정리한 것이다. 세부 근거의
원문 인용은 `backend/docs/대응가이드_근거_정리본.md`에 더 자세히 있고, 여기서는 그걸
요약·연결해서 "화면에서 무엇을 보고 있는 건지"를 설명한다.

## 0. 전체 구성

사이드바는 두 그룹으로 나뉜다.

- **MONITORING**: 종합 관제 / 네트워크 토폴로지 / 실시간 모니터링 / AI 장애 진단
- **MANAGEMENT**: 장애 시뮬레이션 / 이벤트 이력 / AI 코파일럿

3개 공장(사이트)을 동시에 다룬다 — 1공장(생산라인 A, 포트 5020), 2공장(생산라인 B, 포트
5021), 3공장(생산라인 C, 포트 5022). 각 공장은 독립적으로 정상(A)/지연 장애(B)/유실
장애(C)/복합 장애(D) 중 한 상태에 있고, 레이아웃(`app/layout.tsx`)이 3초마다 한 번만
전체 사이트를 폴링해서 모든 화면이 그 결과를 공유한다(페이지를 옮겨 다녀도 다시 안 기다림).

**모든 화면에서 지키는 원칙**: "실제 주입된 시나리오(ground truth)"와 "AI가 샘플 1건을 보고
매긴 순간 판단(AI 즉시 예측)"을 항상 구분해서 보여준다. 유실·복합 장애는 개별 요청 대부분이
정상처럼 보이기 때문에, AI 순간 판단만 믿으면 장애 중에도 정상/이상이 계속 깜빡인다. 그래서
"장애냐 아니냐"는 항상 ground truth 기준으로 판단하고, AI 순간 판단은 참고용으로 별도 표시한다.
또한 백엔드가 실제로 주지 않는 데이터(예: TCP 재전송 세그먼트 수, 장비별 IP)는 화면에 지어내지
않고 "-" 또는 안내 문구로 그 사실을 그대로 보여준다.

## 1. 화면별 소개와 기능

### 1.1 종합 관제 (`/`)

3개 공장 전체를 한눈에 보는 첫 화면.

- **KPI 카드 8개**: 전체 사이트 / 정상 사이트 / 경고 사이트(지연 중) / 위험 사이트(유실·복합 중)
  / 평균 RTT / 평균 Jitter / 손실 감지 사이트(수) / 패킷 손실률(%, 최근 수신 구간 기준). TCP
  재전송 세그먼트 수는 실제로 수집하지 않는다는 안내가 KPI 밑에 붙어 있다.
- **사이트별 네트워크 상태 카드**: 공장명, 포트, 실시간 RTT·Loss·Jitter, AI 순간 진단 + 신뢰도,
  쿨다운 상태, 마지막 데이터 수신 시간, 그리고 "모니터링 →" / "AI진단 →" 버튼(누르면 그 공장이
  자동 선택된 채로 해당 화면으로 이동).
- **네트워크 장애 추이**: 최근 수집된 데이터(최대 200건, 폴링 창)에서 분 단위로 장애 발생/정상
  복구 횟수를 막대그래프로 집계하고, 장애유형(지연/유실/복합)별 발생 건수도 같이 보여준다.
  백엔드에 별도 이력 저장소가 없어서 "최근 수집 데이터 기준"이라는 걸 제목에 명시한다.
- **최근 주요 이벤트**: 최신 장애발생/복구 이벤트 8건, 심각도 배지와 "상세 →"(이벤트 이력 화면
  으로 그 사이트 필터링해서 이동) 링크.

### 1.2 네트워크 토폴로지 (`/topology`)

PLC/센서 → 네트워크 스위치 → Modbus TCP 서버, 3단 구조의 **개념도**.

- 백엔드가 실제 장비 간 물리적 배선 정보를 주지 않기 때문에, 화면 상단에 "개념도입니다"라는
  안내가 항상 떠 있다. 포트 번호와 상태(정상/장애)만 실제 데이터이고 나머지 배치는 실제 현장
  배선과 다를 수 있다.
- 연결선과 장비 테두리는 그 사이트의 현재 시나리오 색(정상=초록/지연=노랑/유실=빨강/복합=보라)
  으로 표시된다. 다만 백엔드가 구간(링크)별 상태를 따로 주지 않으므로, 한 사이트 안의 모든
  링크는 항상 같은 색이다(구간별로 다른 상태를 지어내지 않음).
- 장비를 클릭하면 우측에 상세 패널이 뜬다 — Modbus TCP 서버 노드만 실측값(포트, RTT/Loss/
  Jitter, 데이터 소스)을 보여주고, PLC/스위치 노드는 "개별 식별 정보는 제공되지 않는다"는 점을
  그대로 밝힌다.
- 사이트 탭으로 3개 공장의 토폴로지를 전환해서 볼 수 있다.

### 1.3 실시간 모니터링 (`/monitoring`)

RTT / Packet Loss / Jitter 그래프를 3초 간격으로 갱신.

- 그래프는 Recharts 기반이며 마우스를 올리면 정확한 값이 툴팁으로 뜬다.
- RTT 그래프에는 **RTO 최소 임계치(200ms, RFC 6298)** 참조선이 있다 — 이 선을 넘는다고 바로
  장애가 아니라 "재전송 추정이 걸릴 수 있는 최소 조건"이라는 뜻이다(자세한 알고리즘은 2.2절).
- 장애를 주입한 시점은 "주입" 세로선으로 표시된다.
- 그래프 아래 **Brush**(드래그 슬라이더)로 구간을 확대해서 볼 수 있고, **일시정지/재개** 버튼으로
  화면에 보이는 구간만 그 순간 상태로 얼려둘 수 있다(다른 화면의 실시간 폴링에는 영향 없음).
- **사이트 비교** 드롭다운으로 다른 공장의 그래프를 아래에 나란히 띄울 수 있다(두 공장의 수신
  시각이 서로 다를 수 있어 한 그래프에 억지로 겹치지 않고 따로 보여준다).
- "최근 50/100/200건" 버튼으로 보여줄 범위를 조절한다(다시 네트워크를 타지 않고 이미 받은
  데이터에서 자른다).

### 1.4 AI 장애 진단 (`/diagnosis`)

사이트별로 "실제 시나리오"와 "AI 순간 판단"을 나란히 보여주고, 장애 중이면 세부 진단까지
추천한다.

- 각 카드: 실제 시나리오 배지, AI 순간 판단 + 신뢰도, 실측값(RTT/Loss/Jitter).
- **신뢰도 변화 추이**: 이미 폴링된 데이터에서 AI 신뢰도(확률)만 뽑아 작은 꺾은선 그래프로
  보여준다.
- 장애 중이면 **세부 진단**(지연/유실/복합 11가지 사례 중 하나, 2절 참고)과 조치 절차, 그리고
  "이 진단의 근거가 된 현재 실측값"을 같이 보여준다(진단 근거와 실측값을 바로 연결).
- **장애 유형별 진단 결과 비교** 표: 3개 사이트의 실제 시나리오/AI 순간판단/신뢰도/세부 사례를
  한 표로 모아서 비교한다.
- 하단 "최근 진단 이력"에 장애발생/복구 전환 이벤트 10건이 시간순으로 뜬다.

### 1.5 장애 시뮬레이션 (`/scenario`)

장애를 직접 주입하거나(버튼 4개: 정상/지연/유실/복합), 5분마다 자동으로 무작위 주입되는 것을
지켜보며 **초동 조치 체크리스트**로 대응 연습을 하는 화면.

- 사이트별 카드에 그래프 + 체크리스트가 같이 있어서, 어느 그래프가 어느 체크리스트 건지 다시
  찾아 맞출 필요가 없다.
- **경과 시간**: 이 화면이 그 사이트의 장애 전환을 감지한 순간(수동 주입이든 5분 자동 주입이든)
  부터 "⏱ 경과 00:00"을 1초 단위로 보여준다. 백엔드가 실제 장애 시작 시각을 따로 기록하지
  않기 때문에 "이 화면이 감지한 시점부터"라는 의미다.
- **주입 전/후 비교**: 장애를 직접 주입했을 때만(자동 주입은 기준점이 없어 생략) 주입 직전/
  직후 구간의 평균 RTT·Loss·Jitter를 박스로 비교해서 보여준다.
- **초동 조치 체크리스트**: AI가 추천한 세부 사례(2절의 11가지 중 하나)에 따라 1~3개 조치
  항목이 뜨고, 하나씩 눌러서 완료 표시한다. 전부 완료하면 자동으로 정상 상태로 복귀하고 1분간
  그 공장에는 새 장애가 걸리지 않는다(쿨다운).
- **복구 전/후 비교**: 체크리스트를 다 완료한 순간, "복구 직전 최근 10건 평균"과 "장애 지속
  시간"을 얼려서 저장해두고, 복구 후에는 그 스냅샷과 "현재(실시간)" 값을 비교 카드로 보여준다.

### 1.6 이벤트 이력 (`/logs`)

3개 사이트의 진단 이력을 표로 보며 검색·필터링·내보내기 하는 화면.

- 필터: 사이트, 심각도(INFO/WARN/DANGER/CRITICAL/RECOVERED), 진단명 키워드, **기간(날짜/시간
  범위)**.
- 행을 클릭하면 상세 모달(시간/사이트/AI진단/레벨/RTT·Loss·Jitter/변화)이 뜬다.
- **장애 지속시간 요약**: `fault_started` → 그다음 `recovered` 이벤트를 같은 사이트끼리 짝지어
  지속시간을 계산한다. 아직 복구되지 않은(짝이 없는) 장애는 지속시간을 지어내지 않고 제외한다.
- CSV 내보내기로 지금 필터링된 행을 그대로 파일로 저장할 수 있다.

### 1.7 AI 코파일럿 (`/copilot` 페이지 + 우측 하단 플로팅 위젯)

매뉴얼 기반 대응 보조 챗봇. 전체 화면(`/copilot`)과 모든 화면에서 열 수 있는 플로팅 위젯 두
곳에서 쓸 수 있고, 같은 대화 로직(`useCopilotChat`)을 공유하되 대화 내역은 서로 독립적이다.

- 왼쪽(전용 페이지)엔 매뉴얼 문서 목록(지금은 5개, 2.2절 참고)을 직접 훑어볼 수 있다.
- **공장 선택기**(플로팅 위젯): 어느 공장 이야기인지 직접 고를 수 있다. 질문 텍스트에 "2공장"
  이라고 적어도 그 자체로는 인식되지 않기 때문에(질문 텍스트는 매뉴얼 검색에만 쓰임), 반드시
  이 선택기로 공장을 지정해야 그 공장의 실측값 기준으로 답한다. 다른 화면의 "코파일럿에게
  물어보기" 버튼으로 열면 선택기도 자동으로 그 공장에 맞춰진다.
- **추천 질문 2종류**:
  - 전체 네트워크 질문(별도 줄): "현재 전체 네트워크 상태를 요약해 줘", "가장 심각한 장애가
    발생한 사이트는?", "현재 발생한 장애의 원인을 분석해 줘", "장애 복구를 위한 우선순위를
    알려줘", "TCP 재전송과 RTO의 관계를 설명해 줘".
  - 공장별 빠른 질문: 그 공장의 현재 시나리오에 맞춰 2개씩 바뀐다(예: 유실 장애면 "케이블
    차폐 접지 점검 순서는?", "CRC 에러 확인법은?").
- 답변마다 "출처"가 표시되고, 로컬 LLM(Ollama)을 못 쓰면 "· 간이 응답(매뉴얼 원문)"이라고
  솔직하게 표시한다(매뉴얼 원문을 그대로 조합해서 보여준다는 뜻).

## 2. 대응가이드 정리 — 11가지 세부 사례

AI가 추천하는 조치 가이드는 단순히 "지연/유실/복합" 3종류가 아니라, 실측 데이터 분포를 기반으로
더 세분화한 **11가지 세부 사례**(`backend/fault_tiers.py`)다. 전체 근거의 원문 인용(어느 PDF
몇 페이지)은 `대응가이드_근거_정리본.md`에 있고, 여기서는 구조만 요약한다.

### 2.1 전체 구조

| 장애 유형 | 사례 | 이름 | 구분 기준 | 실측 비율 |
|---|---|---|---|---|
| 지연(B) | `b1` | 순수 지연 | 최근 15건 중 RTO 초과 0건 | 83.5% |
| 지연(B) | `b2` | 재전송 신호 혼재 | RTO 초과 1건 이상 | 16.5% |
| 유실(C) | `c0` | 0단계(신호 없음) | RTO 초과 0건 | 21.0% |
| 유실(C) | `c1` | 1단계(경미) | RTO 초과 1건 | 31.5% |
| 유실(C) | `c2` | 2단계(중간) | RTO 초과 2건 | 30.3% |
| 유실(C) | `c3` | 3단계(심함) | RTO 초과 3건 | 12.4% |
| 유실(C) | `c4` | 4단계(매우 심함) | RTO 초과 4건 이상 | 5.1% |
| 복합(D) | `d1` | 전환 초기(분석 중) | 장애 전환 후 5초 미만 | 69.6% |
| 복합(D) | `d2_low` | 손실 비중 낮음 | 5초 이후, 손실률 30% 미만 | 45.5%* |
| 복합(D) | `d2_mid` | 손실 비중 중간 | 5초 이후, 손실률 30~60% | 24.2%* |
| 복합(D) | `d2_high` | 손실 비중 높음 | 5초 이후, 손실률 60% 이상 | 30.3%* |

*는 "실제 장애 구간(5초 이후)" 안에서의 비율.

### 2.2 분류 알고리즘 — RFC 6298 + Karn RTO 추정

"RTO 초과"는 TCP 재전송 기준시간(RFC 6298: `RTO = max(200ms, SRTT + 4×RTTVAR)`)을 넘겨
응답이 온 경우를 뜻한다. 이 프로젝트는 실제 TCP 재전송 세그먼트 수(`retrans_segs`)를 라이브
경로에서 직접 수집하지 않는 대신, 매 샘플(RTT, loss_flag)마다 SRTT/RTTVAR를 갱신해가며 RTO를
추정하고, RTT가 그 RTO를 넘으면 "재전송이 있었을 가능성이 높은 샘플"로 표시한다. Karn
알고리즘에 따라 그렇게 추정된 샘플은 SRTT/RTTVAR 갱신에서 제외해 튄 값이 평균 자체를 같이
튀게 만들지 않도록 한다(`backend/fault_tiers.py`의 `_tcp_rto_features()`).

- 지연(B): 최근 15건 중 RTO 초과가 하나라도 있으면 `b2`, 없으면 `b1`.
- 유실(C): 최근 15건 중 RTO 초과 건수(0~4건 이상)를 그대로 단계로 씀.
- 복합(D): 장애 전환 후 첫 5초는 `d1`(과도구간). 그 이후는 RTO 초과가 거의 0이 되므로(응답
  자체가 없는 샘플이 대부분이라) 대신 손실률로 3단계를 나눔.

### 2.3 근거 문서 3종과 역할

| 문서 | 성격 | 이 프로젝트에서 뒷받침하는 것 |
|---|---|---|
| **NIST SP 800-82 Rev.3** (`NIST.SP.800-82r3.pdf`) | 미국 NIST의 OT 네트워크·보안 가이드 | 지연·지터 기준의 설비별 차이, 통신 끊김 시 fail-safe, 이중화, 수동 운전 전환, 차폐·접지 |
| **KOSHA GUIDE E-96-2011** (비상정지장치 설계 기술지침) | 한국 산업안전보건공단 안전조치 문서 | 사람(작업자) 안전 최우선, 비상정지 신호 우선 |
| **KOSHA GUIDE G-135-2021** (스마트팩토리 안전시스템 평가 기술지침) | 한국 산업안전보건공단 안전조치 문서 | 통신 이상 시 경보, 안전 전용 네트워크 분리, AI 기반 정지원인 분석 방향성 |

**두 기능에서 문서가 쓰이는 방식은 다르다.**

```
① 11가지 세부 대응가이드 (규칙 기반, 이 2절)
   실측 데이터 → 사례 판정 → 대응가이드 표시
   각 조치 문구의 근거 = PDF 3종 원문을 사람이 직접 대조해 fault_tiers.py에 기록

② AI 코파일럿 (RAG, 3절)
   NIST SP 800-82 (Rev.2) → 팀이 장애별 매뉴얼로 재정리 → manual_knowledge_base.json
   질문 → 매뉴얼 검색 → LLM 답변
   (PDF 3종은 코파일럿이 검색하지 않는다. KOSHA 문서는 코파일럿 경로에 없다)
```

### 2.4 조치 문구별 근거 (원문 대조 완료)

PDF쪽 = 뷰어 기준 페이지, 인쇄쪽 = 문서에 찍힌 쪽수. NIST는 PDF쪽 − 17 = 인쇄쪽.

| 대응가이드 문구 (사례) | 판정 | 문서 | PDF쪽 / 인쇄쪽 | 위치 | 원문 |
|---|---|---|---|---|---|
| 지연을 설비별 기준으로 판단 (`b1`) | ✅ | NIST r3 | 46 / 29 | §2.4 "Timeliness and performance requirements" | "…the criterion for acceptable levels of delay and jitter dictated by the individual installation." |
| 통신 끊김 시 fail-safe 확인 (`c1`~`c4`) | ✅ | NIST r3 | 96 / 79 | §5.3.1 Cyber-Related Safety Considerations | "Cyber-related events, such as the loss of network communications, could trigger these fail-safe events." |
| 통신 이상 시 상태경보 확인 (`c1`~`c4`) | ✅ | G-135 | 23 / -20- | 안전제어시스템 분야 문항 90 | "안전PLC와 제어기기의 통신이 올바르지 않을 경우 상태경보등 또는 경보음을 발생시키는가?" |
| 안전 네트워크 분리 (`c1`~`c4`) | ✅ | G-135 | 16 / -13- | 정보(통신)운영기술 분야 문항 26 | "…별도의 안전 전용 네트워크가 구성되어 있는가?" |
| 차폐 케이블·접지 점검 (`c1`~`c4`) | ⚠️ 부분 | NIST r3 | 118 / 101 | §6.2.1.2 Physical Access Controls > Cabling | "…consider using alternative cabling or shielding that provides suitable protection against environmental threats." |
| 〃 | ⚠️ 부분 | NIST r3 | 194 / 177 | Appendix C.2.2, Table 17 | "Proper shielding, grounding, power conditioning, and/or surge suppression is recommended." |
| 사람 안전 최우선 (`d2_*`) | ✅ | E-96 | 7 / -5- | 4.1 일반 요구사항 (7) | "비상정지 신호(Command)는 다른 어떠한 작동신호보다 우선으로 한다." |
| 〃 | ✅ | NIST r3 | 48 / 31 | §2.4 IT vs OT 비교표, Risk Management Requirements | "Human safety is paramount, followed by protection of the process." |
| 이중화 경로·자동 절체 확인 (`d2_*`) | ✅ | NIST r3 | 20 / 3 | Executive Summary | "Critical components should have a redundant counterpart." |
| 〃 | ✅ | NIST r3 | 46 / 29 | §2.4 "Availability requirements" | "Some OT employ redundant components…" |
| 수동 운전 모드 전환 준비 (`d2_high`) | ✅ 원칙 | NIST r3 | 20 / 3 | Executive Summary | "…graceful degradation, such as moving from "normal operation" … to "manual operation" with no automation." |
| (참고) AI 원인 분석 방향성 | 📎 | G-135 | 16 / -13- | 문항 29~31 | "…AI(인공지능)이 스스로 정지원인 분석을 수행할 수 있는가?" |

- **PDF가 아니라 이 프로젝트 데이터가 근거인 것**: `b2` 재전송 혼재 구분, `d1` 과도구간, 모든 사례의 단계별 비중(%).
- **3개 PDF 모두에 근거 없음 (팀 작성 절차)**: CRC/FCS 에러 확인, flapping 로그 점검, 광케이블 교체, QoS/CoS·드롭 카운터·대역폭 제한.
  "CRC", "FCS", "flap"을 키워드로 검색해도 3개 PDF 모두 0건이었다.
- **근거로 쓰지 않는 것**: NIST 138쪽 mesh "preemptive fail-over"(무선 메시 맥락), G-135 36쪽 "센서나 스위치를 이중화"(안전스위치 회로 이중화이지 네트워크 이중화가 아님).

모든 인용은 `backend/docs/references/`의 원문 PDF를 직접 검색해 페이지·조항을 대조한 것이다.
"원문 그대로 인용"과 "팀이 취지를 재정리한 설명"은 항상 구분해서 표기한다.

## 3. AI를 활용한 대응가이드 (AI 코파일럿)

### 3.1 구조 — 경량 RAG + 선택적 로컬 LLM

```
질문 + (선택된 공장의 현재 시나리오/실측값)
  → TF-IDF 코사인 유사도로 매뉴얼 문서 1건 검색
  → (Ollama 로컬 LLM이 떠 있으면) 그 문서 내용으로 답변 재구성
  → (LLM을 못 쓰면) 매뉴얼 원문을 그대로 조합해 응답 + "간이 응답" 표시
```

- 매뉴얼은 `backend/docs/manual_knowledge_base.json`에 있는 짧은 문서들(현재 5개, 아래
  3.2절)뿐이고, 그 이상의 내용을 지어내지 않는다.
- Ollama는 완전히 선택 사항이며, 3초 타임아웃 안에 응답이 없거나 설치되어 있지 않으면 예외
  없이 매뉴얼 원문 조합(fallback)으로 넘어간다. 이 fallback 여부는 항상 `fallback_used`로
  프론트에 전달되어 "· 간이 응답(매뉴얼 원문)"으로 숨김없이 표시된다.
- 코파일럿 모듈(`backend/copilot.py`)은 실시간 진단 로직(`api/main.py`의 `/predict` 등)과
  완전히 독립적인 모듈이라, 여기서 문제가 나도 실시간 진단 경로에는 영향이 없다.

### 3.2 지식베이스 문서 5개

| doc_id | 주제 | 근거 |
|---|---|---|
| ICS-NET-01 | 지연 장애 (Delay) | NIST SP 800-82 Rev.2 §5.8.11 |
| ICS-NET-02 | 유실 장애 (Loss) | NIST SP 800-82 Rev.2 §6.2.11.3 |
| ICS-NET-03 | 복합 장애 (Combined) | NIST SP 800-82 Rev.2 §5.6, §5.13 |
| ICS-NET-04 | 정상 상태 (Normal) | NIST SP 800-82 Rev.2 §5.16 |
| ICS-NET-05 | 진단 알고리즘 설명 (TCP 재전송/RTO) | RFC 6298 + Karn's Algorithm, `fault_tiers.py`의 실제 구현 설명 |

- 이 매뉴얼은 NIST SP 800-82 **Rev.2**를 참고해 팀이 장애 유형별로 재정리한 것이다. 표준 원문을
  그대로 옮긴 것이 아니며, `reference`는 "참고 출처"이지 "원문 발췌"가 아니다(파일의 `meta`에도 명시).
- 프로젝트가 보유한 PDF는 Rev.3이다. Rev.2는 2023-09-28 철회되어 Rev.3으로 대체되었다.
- KOSHA 안전조치 문서(E-96, G-135)는 이 지식베이스에 포함되어 있지 않다.

ICS-NET-05는 2.2절에서 설명한 RTO 추정 알고리즘을 그대로 설명한 문서다 — "TCP 재전송과
RTO의 관계를 설명해 줘" 같은 질문에, 실제로 존재하는 코드를 설명하는 것이라 허위 생성이 아니다.

### 3.3 "어느 문서를 고를지" 검색 로직

질문 텍스트만으로 코사인 유사도를 계산해서, 1위 점수가 일정 기준(0.12) 이상이면 질문 자체가
충분히 구체적이라고 보고 그 결과를 그대로 쓴다. 점수가 그보다 낮으면("지금 어떻게 해야해?"처럼
질문 자체에 단서가 거의 없는 경우) 그제서야 지금 선택된 공장의 현재 장애 유형에 해당하는
문서로 기본 라우팅한다. (초기 버전은 현재 장애 유형 힌트를 질문 앞에 항상 이어붙이는 방식이었는데,
이러면 "TCP 재전송과 RTO의 관계를 설명해 줘"처럼 구체적인 질문도 엉뚱하게 현재 장애 문서로
끌려가는 문제가 있어서, 질문 자체의 확신도를 먼저 보는 지금 방식으로 바꿨다.)

### 3.4 공장 단위·전체 질문 구분

- **공장 선택기로 물어보는 질문**(개별 공장 실측값 포함)은 위 3.1~3.3 경로 그대로 백엔드
  매뉴얼 검색을 탄다.
- **"현재 전체 네트워크 상태를 요약해 줘" / "가장 심각한 장애가 발생한 사이트는?"** 이 2개는
  성격이 다르다 — 매뉴얼 5개는 장애 유형 하나에 대한 설명일 뿐 "지금 3개 공장 중 어디가 제일
  심각한지"는 알 길이 없다. 그래서 이 2개 질문은 백엔드를 아예 타지 않고, 지금 화면에 이미
  올라온 실시간 사이트 상태에서 프론트가 직접 답을 구성한다. "가장 심각한 사이트" 판단은 AI의
  순간 신뢰도(유실·복합에서 흔들릴 수 있음)가 아니라, 백엔드의 시나리오별 고정 심각도(정상=ok,
  지연=warning, 유실=danger, 복합=critical)를 기준으로 한다.

### 3.5 발표용 한 줄 설명

> 총 3개의 문서를 찾았습니다. E-96-2011, G-135-2021은 KOSHA 안전조치 문서이고, NIST SP 800-82r3는
> OT 네트워크 및 보안 가이드입니다. NIST 가이드를 바탕으로 장애별 대응 매뉴얼(.json)을 만들어 AI
> 코파일럿에 RAG 기술을 적용했고, 3개 문서 모두 11가지 세부 장애 사례(지연·유실·복합)의 대응가이드
> 근거를 확인하는 데 썼습니다.
