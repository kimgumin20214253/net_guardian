# NetGuardian 백엔드 — 파일 구조와 작동 순서 정리

작성일: 2026-10-10
목적: 수집(netem 장애 주입) → 분석(TCP RTO 방식) → 검증(실측 재전송 대조)까지 이어지는 전체 파이프라인을
처음 보는 사람도 이해할 수 있도록 "각 파일이 뭘 하는지"와 "어떤 순서로 실행되는지"를 정리한다.

## 0. 큰 그림 (택배 비유로 한 줄 요약)

```
[장애 주입기] 가 네트워크를 일부러 나쁘게 만듦
      ↓
[서버] 는 그 나쁜 네트워크 위에서 평범하게 응답함
      ↓
[수집기] 는 응답이 오고 가는 걸 재면서 "이번엔 몇 ms 걸렸나, 응답이 왔나 안 왔나"를 한 줄씩 기록함
      ↓
[분석 스크립트] 들이 쌓인 기록을 가지고 "정상/지연/유실/복합을 얼마나 잘 구별하는가"를 계산함
      ↓
[검증 스크립트] 가 "우리 추정이 실제 운영체제 재전송 기록과 맞는지"까지 한 번 더 대조함
```

## 2. 핵심 파일별 상세 역할

### ① `network/server.py` — 모의 산업 제어 서버
- Modbus TCP 서버. 포트 5020에서 "쓰기 1회 + 읽기 1회" 요청을 받아 응답한다.
- `.current_label`을 읽어서 **B(지연)일 때 직접 `time.sleep()`으로 응답을 늦추고, C/D(유실)일 때 가끔 타임아웃이 나도록 일부러 응답을 묶어둔다.** 숫자를 지어내는 게 아니라 서버가 실제로 늦게 답하므로, 클라이언트가 재는 RTT는 전부 진짜 걸린 시간이다.
- `NG_SERVER_FAULTS` 환경변수로 이 기능을 끌 수 있다. **tc netem으로 수집할 때는 반드시 꺼야 한다** — 안 그러면 netem 장애 위에 서버 장애가 또 겹쳐서 이중으로 나빠진다.

### ① `network/master_collector.sh` — 장애 자동 순환 주입기
- 리눅스의 `tc netem` 명령으로 루프백(lo) 네트워크 자체에 지연/손실을 건다 (서버 코드를 건드리는 게 아니라 네트워크 계층에서 실제로 패킷을 늦추거나 버림).
- A(정상, 30초) → B(지연, 30초) → A → C(유실, 30초) → A → D(복합, 5+3+7+5초) 순서를 무한 반복하면서, 바뀔 때마다 `.current_label`에 그 글자를 써준다.
- 이 라벨 파일이 **정답(ground truth)** 역할을 한다 — packet_analyzer.py가 그 순간 기록하는 모든 줄에 이 라벨을 그대로 붙인다.

### ② `packet_analyzer.py` — 수집기 (가장 중요한 파일)
- 0.1초마다 한 번씩 "레지스터 쓰기 + 읽기"를 동시에 보내고, 응답이 올 때까지 걸린 시간을 잰다.
- 1초 안에 응답이 없으면 실패로 보고 `loss_flag=1`, RTT 칸에는 5000ms라는 표식값을 넣는다 (실패했으니 실제 시간을 잴 수 없어서 넣는 약속된 값).
- 직전 요청과의 RTT 차이를 `jitter`로 기록한다.
- 그 순간 `.current_label`에 적힌 값을 `label`로 기록한다.
- **`PA_LOG_RETRANS=1`을 켜면** 요청 직전·직후에 `/proc/net/snmp`(리눅스가 호스트 전체 TCP 상태를 세어 두는 파일)를 읽어서, 그 사이에 운영체제가 실제로 재전송한 횟수(`retrans_segs`)와 보낸 패킷 수(`out_segs`)까지 같이 기록한다. 끄면 예전과 똑같은 5개 열짜리 파일이 나온다.
- 결과는 `data/` 폴더 밑에 CSV로 한 줄씩 계속 추가된다 (파일명은 `PA_OUTPUT_FILE`로 바꿀 수 있음).

### ③~⑤ 수집 데이터 폴더
| 폴더 | 언제·어떻게 수집 | 용도 |
|---|---|---|
| `raw_dataset_20260904/` | 1차, A/B/C/D 각각 따로 파일 | **학습용** 원본 데이터 (22,873건) |
| `raw_dataset_20261004/` | 2차, 재수집 세션 + 일반화(다른 강도) 세션 + 60초 nstat 재전송 측정 | 모델이 **다른 날·다른 강도**에서도 통하는지 검증 |
| `raw_dataset_20261009/` | 3차, `verify_retrans.csv` 하나 (약 30분, 10,988건) | 요청 하나하나마다 **실제 재전송 여부(정답)** 까지 포함 → 우리 추정이 맞는지 대조 |

### ⑥ 기본 학습/평가 스크립트
- **`train_and_benchmark.py`**: `raw_dataset_20260904/`의 4개 파일을 합쳐서 Logistic Regression, Decision Tree, Random Forest, LightGBM 4개 모델을 학습하고 정확도를 비교한다. 가장 좋은 모델을 `models/`에 저장한다.
- **`evaluate.py`**: 저장된 모델을 불러와 정확도·정밀도·재현율·F1과 4×4 혼동행렬을 출력한다.
- **`measure_latency.py`**: 모델이 한 번 추론하는 데 실제로 몇 ms 걸리는지(엣지 환경 적합성 논거용) 수천 번 반복해서 중앙값/p95/p99를 잰다.
- **`eval_timesplit.py`**: 무작위로 섞지 않고 **시간 순서 그대로** 5구간으로 나눠 검증한다(미래 데이터가 과거 학습에 섞이는 걸 방지). 윈도우(최근 15개) 특징을 추가한 Decision Tree와도 비교한다.

### ⑦ `analyze_followup.py` — 2차 수집 심화 분석
`raw_dataset_20261004/`를 가지고 5가지를 계산해 `results_20261004/`에 저장한다: 재수집·일반화 세션 성능, 일반화 세션에서 지연 구간별로 RTT가 얼마나 벗어났는지, 복합 장애 첫 5초(지연과 구별 안 되는 구간) 통계, 유실 표식값(5000ms)을 바꿔도 결과가 똑같은지, 60초 재전송 측정 요약.

### ⑧ `eval_tcp_features.py` — TCP RTO 방식 특징 비교 (교수님 심화 피드백 핵심)
- "유실은 타임아웃이 아니어도, TCP가 알아서 재전송해서 복구하면 RTT가 순간적으로 평소보다 늘어난다"는 원리를 이용한다.
- RFC 6298 공식 그대로 **SRTT(평균)**, **RTTVAR(변동폭)**, **RTO(재전송 기준 시간 = SRTT + 4×RTTVAR, 최소 200ms)**를 요청 순서대로 계산한다.
- 응답이 RTO를 넘겨서 왔다면 "재전송이 있었을 것"으로 보고 **최근 15개 중 이런 경우가 몇 번인지 비율**을 새 특징(`rto_exceed_w`)으로 만든다.
- 이때 재전송으로 추정되는 샘플은 평균(SRTT) 계산에서 빼야 평균이 왜곡되지 않는다. 다만 "가끔 튀는 것"(재전송)과 "계속 늦어지는 것"(진짜 지연 장애의 시작)을 구별해야 하므로, 한 번만 튀면 빼고 **연속으로 튀면** 지연으로 보고 평균에 반영한다(`karn` 모드).
- 기본/+윈도우/+TCP방식/전체, 이 4가지 특징 조합을 **전부 같은 Random Forest**로 비교해서 어떤 조합이 유실을 가장 잘 잡아내는지 표로 만든다.

### ⑨ `eval_verify_retrans.py` — 실측 검증 (가장 최근에 추가됨)
- ⑧에서 계산한 "RTO 초과"는 **추정**일 뿐이다. 이 스크립트는 `raw_dataset_20261009/verify_retrans.csv`에 들어있는 **실제 재전송 횟수(정답)**와 요청 하나하나를 대조해서, 그 추정이 얼마나 정확한지(정밀도)와 얼마나 많이 잡아내는지(탐지율)를 계산한다.
- 추가로 원본 데이터로 학습해 둔 모델을 이번 새 데이터에 그대로 적용해서, 전혀 다른 날 수집한 데이터에서도 성능이 유지되는지까지 같이 확인한다.

### 결과/문서 폴더
- **`results_tcp_features/`**: ⑧⑨의 결과. `feature_comparison.csv`(특징 조합별 성능), `rto_exceed_vs_retrans.csv`(60초 단위 추정 vs nstat 실측), `verify_summary.csv`/`verify_rto_vs_retrans.csv`/`verify_model_performance.csv`(요청 단위 검증 3종).
- **`figures/`**: 논문용 흑백 그림. `make_figures.py`가 만든다.
- **`models/`**: 학습이 끝난 모델 파일(`.pkl`)과 혼동행렬 이미지. `api/main.py`가 이걸 불러와 대시보드에 서빙한다.
- **`docs/`**: 실행 방법, 환경 구축 방법, 교수님 피드백 대응 계획 등 팀 공유 문서.

## 3. 전체 작동 순서 (맨 처음부터 논문 숫자가 나오기까지)

### 단계 A. 데이터 수집 (리눅스 환경, 터미널 3개 동시 실행)
```
터미널 1:  NG_SERVER_FAULTS=0 python network/server.py
터미널 2:  python packet_analyzer.py                 (또는 PA_LOG_RETRANS=1 PA_OUTPUT_FILE=... 로 재전송까지 기록)
터미널 3:  bash network/master_collector.sh
```
1. 터미널 3이 30초(또는 D는 5+3+7+5초)마다 장애 종류를 바꾸고 `.current_label`에 적는다.
2. 동시에 `tc netem`이 리눅스 커널 네트워크 계층에서 실제로 그 장애(지연/손실)를 건다.
3. 터미널 1의 서버는 장애 재현 기능이 꺼진 채로, 그 나빠진 네트워크 위에서 평범하게 응답한다.
4. 터미널 2의 수집기는 0.1초마다 요청을 보내고, 응답까지 걸린 시간/성공 여부/그 순간의 라벨을 한 줄씩 CSV에 쌓는다.
5. 원하는 시간만큼(30분~수 시간) 쌓은 뒤 터미널 3 → 2 → 1 순서로 Ctrl+C, 마지막에 `sudo tc qdisc del dev lo root`로 장애 설정을 지운다.

→ 이 과정을 9월 4일(1차, 학습용), 10월 4일(2차, 검증용 + 60초 nstat 측정), 10월 9일(3차, 요청 단위 재전송 정답 포함)에 각각 실행해서 `raw_dataset_20260904/`, `raw_dataset_20261004/`, `raw_dataset_20261009/`가 만들어졌다.

### 단계 B. 기본 모델 학습 및 평가
```
python train_and_benchmark.py   # 1차 데이터로 4개 모델 학습 → models/ 저장
python evaluate.py              # 정확도/혼동행렬 확인
python measure_latency.py       # 추론 속도 측정
python eval_timesplit.py        # 시간 순서 지킨 교차검증
```
→ "기본 특징(RTT/손실/지터)만으로는 유실 재현율이 0.51 정도"라는 **문제점**이 여기서 드러난다.

### 단계 C. 2차 데이터로 재현성·일반화 확인
```
python analyze_followup.py      # raw_dataset_20261004/ 분석 → results_20261004/
```
→ "같은 조건이면 성능 유지되지만, 처음 보는 강도에서는 떨어진다"는 **한계**를 확인.

### 단계 D. TCP RTO 방식 특징으로 유실 문제 해결 시도
```
python eval_tcp_features.py     # 1차+2차 데이터로 특징 4종 비교 → results_tcp_features/
```
→ "RTO 초과 비율"을 특징으로 추가하면 유실 재현율이 0.51 → 0.93까지 오른다는 **핵심 결과**가 여기서 나온다. 단, 이건 아직 "진짜 재전송과 맞는지"는 60초 단위(nstat)로만 간접 확인한 상태.

### 단계 E. 요청 단위로 실제 재전송과 대조 (가장 최근 단계)
```
(3차 수집: PA_LOG_RETRANS=1로 verify_retrans.csv 생성)
python eval_verify_retrans.py   # 요청 단위 정밀 대조 → results_tcp_features/verify_*.csv
```
→ "RTO 초과로 잡은 것은 94% 확률로 진짜 재전송이었다(정밀도)"는 것과 "다만 전체 재전송의 43%만 잡아낸다(탐지율, RTO 이전에 더 빨리 복구되는 재전송이 있어서)"는 **최종 실측 근거**가 여기서 나온다. 이 결과가 지금 논문 3~4장·표2·표3에 들어간다.

### 단계 F (선택). 실시간 서빙
```
venv\Scripts\python.exe -m uvicorn api.main:app --reload --port 8000   # 모델 서빙 API
cd ../frontend && npm run dev                                           # 대시보드 (localhost:3000)
```
→ 대시보드의 "장애 주입" 버튼은 `.current_label`을 바꾸고, `network/server.py`+`packet_analyzer.py`가 켜져 있으면 실제로 그 장애가 재현되어 대시보드 화면에 실시간 반영된다.
