# Net Guardian 논문 개념 정리

> 논문을 쓰기 전에 팀이 함께 읽는 문서. 위에서부터 순서대로 읽으면 표와 그림이 무엇을 말하는지 이해할 수 있도록 구성했다.
> 숫자는 모두 우리 실측 결과이다.

---

## 0. 이 논문을 한 문단으로

공장 제어망(Modbus TCP)에서 장애가 났을 때, **패킷 내용을 열어보지 않고 응답 시간만 보고** 장애 원인이 "지연"인지 "유실"인지 구별하고 싶었다. 지연은 잘 구별됐지만, 유실은 **TCP가 사라진 패킷을 몰래 다시 보내 주는 바람에(재전송)** 응답이 "없는" 대신 "늦게" 와서 지연처럼 보였다. 그래서 **TCP가 다시 보내기 전에 기다리는 시간(RTO)을 우리도 똑같이 계산해서**, "RTO보다 늦게 온 응답 = 중간에 재전송된 응답"으로 판단했다. 그리고 이 판단이 맞는지 **운영체제가 센 실제 재전송 기록과 대조해서 94%가 맞음**을 확인했다.

## 1. 네트워크 기초

### 1-1. 패킷과 TCP
- 데이터는 **패킷**이라는 작은 조각으로 나뉘어 전달된다.
- **TCP**는 패킷이 빠짐없이, 순서대로 도착하도록 보장하는 약속(프로토콜)이다. Modbus TCP는 이 TCP 위에서 동작한다.

### 1-2. ACK (수신 확인)
- 받는 쪽은 패킷을 받으면 "잘 받았다"는 **ACK**를 보낸다.
- ACK는 **통신의 양 끝(클라이언트와 서버)** 사이에서 오간다. 중간의 라우터는 패킷을 **전달만** 하고 ACK를 보내지 않는다.

### 1-3. 재전송 (Retransmission)
- 보낸 쪽이 일정 시간 안에 ACK를 받지 못하면 "패킷이 사라졌다"고 보고 **같은 패킷을 다시 보낸다.** 이것이 재전송이다.
- 재전송은 **운영체제(TCP)가 알아서** 한다. 프로그램(우리 수집기)은 재전송이 일어났는지 **직접 알 수 없다.** 결과적으로 응답이 늦게 올 뿐이다.

### 1-4. RTT (왕복 시간)
- 요청을 보내고 응답을 받을 때까지 걸린 시간.
- 우리 실험에서 정상일 때 약 3~5ms, 지연 장애일 때 약 290ms.

### 1-5. RTO (재전송 타이머) ← 이 논문의 핵심 개념
TCP는 "얼마나 기다렸다가 다시 보낼지"를 **매번 계산**한다. 이 기다리는 시간이 **RTO**다.

| 값 | 뜻 | 비유 |
|---|---|---|
| **SRTT** | 최근 RTT의 평균 | 평소 배송 시간 |
| **RTTVAR** | 최근 RTT가 얼마나 들쭉날쭉한지 | 배송 시간의 편차 |
| **RTO** | SRTT + 4 × RTTVAR (Linux는 최소 200ms) | "이만큼 지나도 안 오면 분실로 보고 다시 보낸다" |

**왜 RTO 값이 중요한가 (교수님 강조 내용)**
- RTO가 **너무 크면**: 패킷이 사라져도 오래 기다리므로 손실을 늦게 알아챈다.
- RTO가 **너무 작으면**: 조금 늦은 것뿐인데 사라졌다고 착각해서 불필요하게 다시 보낸다.
- 그래서 TCP는 최근 RTT를 보고 RTO를 매번 갱신한다.

**재전송된 RTT는 평균에서 뺀다 (Karn 알고리즘, 교수님 강조 내용)**
- 재전송이 섞인 RTT는 "길이 막혀서 늦은 시간"이 아니라 "사라진 패킷을 기다린 시간"이다.
- 이걸 평균(SRTT)에 넣으면 "평소 배송 시간"이 망가지므로 TCP는 넣지 않는다.

### 1-6. 계산 예시 (우리 데이터 기준)

| 상황 | SRTT | RTTVAR | SRTT + 4·RTTVAR | RTO (최소 200ms 적용) |
|---|---|---|---|---|
| 정상 | 5ms | 1ms | 9ms | **200ms** |
| 지연 장애 | 290ms | 60ms | 530ms | **530ms** |

- **정상 상황**에서 응답이 220ms에 왔다 → RTO(200ms) 초과 → **"중간에 재전송이 있었다"**
- **지연 장애**에서 응답이 350ms에 왔다 → RTO(530ms) 이내 → **"그냥 길이 막혀서 늦은 것"**

**→ 지연은 평균 자체가 올라가서 RTO도 같이 올라가므로 RTO 초과가 잘 안 생긴다. 유실은 평소엔 빠른데 가끔 RTO를 넘는다. 이 차이로 둘을 구별한다.**

### 1-7. 두 계층: 우리가 보는 것과 못 보는 것

```
[TCP 계층 — 운영체제가 처리, 수집기는 못 봄]
클라이언트 ──패킷──X (사라짐)
           ... RTO(200ms) 동안 ACK 안 옴 ...
클라이언트 ──패킷 다시 보냄──→ 서버      ← 재전송
클라이언트 ←────────ACK────────── 서버

[응용 계층 — 수집기가 보는 것]
수집기: Modbus 요청 ............................ Modbus 응답
        |←────────── RTT = 220ms (평소 5ms) ──────────→|
```
수집기는 "응답이 늦게 왔다"만 안다. **재전송이 있었는지는 RTO 계산으로 추정**하고, **운영체제의 재전송 카운터로 정답을 확인**했다.

## 2. 우리 실험의 구조

### 2-1. 테스트베드 (그림 1)
- 한 Linux 컴퓨터 안에서 Modbus **클라이언트(수집기)**와 **서버**를 실행한다.
- 둘 사이의 통로(**루프백 lo**)에서 **tc netem**이 일부러 지연·유실을 만든다.
  - 실제 라우터가 혼잡해서 패킷을 늦추거나 버리는 상황을 **흉내 낸 것**이다.
- 수집기는 0.1초마다 요청을 보내고, 요청마다 다음을 기록한다.

| 기록 | 뜻 |
|---|---|
| rtt | 응답까지 걸린 시간 (1초 안에 응답이 없으면 5000ms로 기록) |
| loss_flag | 1초 안에 응답이 없으면 1 (= 타임아웃) |
| label | 그 순간 netem이 만들고 있던 장애 종류 (정답) |
| retrans_segs | (검증 세션만) 그 요청 동안 운영체제가 센 재전송 횟수 |

### 2-2. 장애 시나리오 (표 1)

| 구분 | netem 설정 | 무슨 상황 |
|---|---|---|
| A 정상 | 지연 1ms | 문제 없음 |
| B 지연 | 120±40ms 지연 | 모든 패킷이 골고루 늦음 |
| C 유실 | Gilbert-Elliott 손실 (p=5%, r=50%) | 패킷이 가끔, **몰려서** 사라짐 |
| D 복합 | 지연·손실·단절 혼합 | (본론에서 강조하지 않음) |

- **Gilbert-Elliott 모델**: 손실이 하나씩 흩어지지 않고 **연속으로 몰려서** 생기게 하는 방식(버스트 손실). 손실 상태에 들어가면 평균 2패킷 동안 이어지고, 평균 손실률은 약 8.2%.
- **lo의 특성**: 지연이 요청과 응답에 각각 걸려서, 120ms로 설정하면 실제 RTT는 약 290ms.

## 3. 문제: 유실이 지연으로 보인다

### 3-1. 무슨 일이 일어나나
```
① netem이 패킷을 버린다 (유실)
② TCP가 RTO(약 200ms) 기다렸다가 다시 보낸다 (재전송)
③ 다시 보낸 패킷이 도착해서 응답이 온다 — 단, 200ms 이상 늦게
④ 수집기 기록: "응답 왔음(유실 아님), 220ms(늦음)" → 지연처럼 보임
```

### 3-2. 숫자로 보면
- 유실 조건 60초 동안 운영체제의 TCP 재전송 비율: **5.67%** (정상 0.12%의 약 46배)
- 그런데 수집기가 기록한 타임아웃(loss_flag=1)은 **2건**뿐
- 대신 150ms를 넘는 늦은 응답이 **37건**
- → 실제로는 유실인데 기록에는 대부분 "늦은 응답"으로 남는다

### 3-3. 그래서 생기는 결과
기본 특징(RTT, 손실 여부, 지터)만 쓴 모델은
- 지연 장애: **재현율 0.99** (잘 맞힘)
- 유실 장애: **재현율 0.51** (절반만 맞힘)

## 4. 해결: 재전송 타이머 특징

### 4-1. 아이디어
TCP가 RTO를 계산하는 방식을 **수집기에서 똑같이** 계산한다. 그리고 응답이 RTO보다 늦게 왔으면 "그 사이 재전송이 있었다"고 추정한다.

### 4-2. 만드는 특징
| 특징 | 계산 |
|---|---|
| SRTT | 최근 RTT 평균 (재전송으로 추정되는 응답은 제외) |
| RTTVAR | 최근 RTT 변동폭 |
| **RTO 초과 비율** | 최근 15개 응답 중 RTO를 넘겨 온 비율 ← 핵심 |

- **"최근 15개"를 보는 이유**: 응답 하나가 아니라 **지금 상황**을 판단하기 위해서다. 최근에 RTO를 넘긴 응답이 섞여 있으면, 지금 응답이 빠르게 왔더라도 "지금은 유실이 일어나는 상황"이라고 판단할 수 있다.
- **연속으로 RTO를 넘기면 평균에 반영**: 지연 장애가 막 시작되면 처음 몇 개는 RTO를 넘긴다. 이걸 계속 빼면 평균이 지연에 적응하지 못하므로, 연속으로 넘기면 "길이 느려졌다"고 보고 반영한다.

### 4-3. 다른 특징들 (비교용)
| 특징 세트 | 내용 | 역할 |
|---|---|---|
| 기본 | RTT, 손실 여부, 지터 | 출발점 |
| 윈도우 | 최근 15개의 손실률, RTT 표준편차 | 종합 점수를 높임 (주인공 아님) |
| **재전송 타이머** | SRTT, RTTVAR, RTO 초과 비율 | **유실 판별을 크게 개선 (주인공)** |

## 5. 평가 지표: 숫자 읽는 법

### 5-1. 재현율 (Recall)
**실제 유실 중에서 모델이 "유실"이라고 맞힌 비율**
- 예: 실제 유실 요청이 100건인데 모델이 51건을 유실로 맞힘 → 재현율 0.51
- 표 2의 숫자가 이것이다.

### 5-2. 정밀도 (Precision)
**모델(또는 방법)이 "그렇다"고 한 것 중에서 실제로 맞은 비율**
- 예: RTO 초과로 "재전송"이라고 판정한 응답 202건 중 190건이 실제 재전송 → 정밀도 94%
- 표 3의 숫자가 이것이다.

### 5-3. 둘의 차이
| | 질문 | 우리 결과 |
|---|---|---|
| 재현율 | 놓치지 않았나? | 유실 0.51 → 0.93 |
| 정밀도 | 잘못 잡지 않았나? | RTO 초과 판정 94% |

### 5-4. Macro F1
정상·지연·유실·복합 **네 유형의 점수를 평균**한 종합 점수. 한 유형이 약하면 같이 내려간다.

## 7. 표와 그림 해설 (무엇을 증명하나)

### 그림 1. 시스템 구성도
- **보여주는 것**: 실험이 어떻게 구성됐는지 (테스트베드 → 특징 추출 → 판별 → 결과)
- **강조**: 낮음. 독자가 실험 구조를 이해하는 용도

### 표 1. 장애 시나리오와 수집 건수
- **보여주는 것**: 어떤 장애를 어떻게 만들었고 데이터가 몇 건인지
- **강조**: 낮음. Gilbert-Elliott 모델을 쓴 이유(버스트 손실)만 본문에서 한 번

### 그림 2. 유실 조건의 요청별 RTT와 실제 재전송 여부 (검증 세션)
- **점 하나** = 요청 1건, **높이** = 응답 시간
- **검은 점** = 운영체제가 실제로 재전송한 요청, **회색 점** = 재전송 없음, **×** = 타임아웃
- **보여주는 것**:
  1. 유실 조건인데 타임아웃(×)은 적다 → **유실이 지연으로 보인다 (문제)**
  2. 200ms 점선 위의 늦은 응답 165건은 **전부 검은 점(실제 재전송)** → **늦은 응답의 원인은 재전송이다 (원인)**
- **강조**: **높음 (핵심 그림)**

### 표 2. 재전송 타이머 특징 추가에 따른 유실 재현율
| 검증 | 기본 | +재전송 타이머 |
|---|---|---|
| 시간 블록 | 0.51 | **0.93** |
| 재수집 세션 | 0.72 | **0.92** |
| 일반화 세션 | 0.43 | **0.83** |
| 검증 세션 | 0.55 | **0.81** |
- **보여주는 것**: 재전송 타이머 특징을 넣으면 유실을 훨씬 잘 맞힌다. 네 가지 검증 **모두에서** 같은 결과 → 우연이 아니다
- **강조**: **높음 (핵심 결과)**

### 표 3. RTO 초과 판정과 실제 재전송 대조 (검증 세션)
| 항목 | 정상 | 지연 | 유실 |
|---|---|---|---|
| RTO 초과 중 실제 재전송 (정밀도) | 100% | 60% | **100%** |
- **보여주는 것**: "RTO보다 늦게 왔으니 재전송이다"라는 우리의 추정이 **실제로 맞다** (전체 94%, 유실 조건 100%)
- **강조**: **높음 (방법이 옳다는 증명)**
- 표의 다른 행(재전송 발생 비율, 탐지율)은 숫자만 두고 본문에서 강조하지 않는다

| 유실인데 왜 타임아웃이 안 나나요? | TCP가 사라진 패킷을 재전송해서 응답이 결국 오기 때문입니다. 대신 늦게 옵니다. |
| RTO를 넘으면 왜 재전송인가요? | TCP는 RTO 동안 ACK가 없으면 다시 보냅니다. 응답이 RTO보다 늦게 왔다면 그 사이 다시 보낸 것입니다. |
| 그게 맞는지 어떻게 아나요? | 운영체제가 센 실제 재전송 횟수와 요청마다 대조했고, 94%가 일치했습니다. 유실 조건에서는 100%였습니다. |
| 지연 장애도 늦게 오는데 헷갈리지 않나요? | 지연은 모든 응답이 골고루 늦어서 평균(SRTT)이 올라가고 RTO도 같이 올라갑니다(예: 530ms). 그래서 RTO 초과가 거의 생기지 않습니다. |
| 재전송 타이머를 바꾼 건가요? | 아닙니다. TCP는 그대로 동작했고, 우리는 TCP의 계산 방식을 빌려 와서 판별 특징으로 썼습니다. |
| 라우터가 ACK를 보내나요? | 아닙니다. ACK는 통신의 양 끝(클라이언트와 서버) 사이에서만 오갑니다. 라우터는 전달만 합니다. |
| 왜 Gilbert-Elliott 모델인가요? | 손실이 하나씩 흩어지지 않고 몰려서 생기는 상황(버스트 손실)을 재현하기 위해서입니다. |
| 실제 공장망에서도 되나요? | 이번 실험은 테스트베드에서 수행했고, 실제 산업망 검증은 향후 과제입니다. |
